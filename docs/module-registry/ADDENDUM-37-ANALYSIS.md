# Addendum 37 — Module Registry & Enablement: reality check & decisions

Spec: SMS-FSD-ADD-037 v1.0 · Register: 320 checklist items · Contract: [API-CONTRACT.md](API-CONTRACT.md) · Tasks: [ADDENDUM-37-TASKS.md](ADDENDUM-37-TASKS.md)

## Part A — spec vs. code

The FSD is written for a greenfield system (React, BIGINT ids, dotted permission codes, a `customers` schema, BOM in
`material`, Hangfire MRP/forecast jobs). Most of what it asks for already exists here under other names. Building the
spec literally would create a **second** feature system, a **second** customer master and a **second** route model
next to the live ones. Every item is therefore mapped onto what exists.

| Spec assumes | Reality | Consequence |
|---|---|---|
| No module system; new `tenant.Modules/OrgModules/...` | `tenant.FeatureDefinitions` (MODULE_/SCREEN_/FEATURE_ codes, IsCore), `PlanFeatureTemplates` (BASIC/STANDARD/ENTERPRISE), `OrganizationFeatures` (per-org IsEnabled), code-defined dependency list, startup backfill, super-admin "Manage Features" page | **Extend this system** (D-1). No parallel tables |
| `[RequiresModule]` middleware, ~30 controllers to tag | `[RequiresFeature]` + global `FeatureAuthorizationFilter` already on **88 controllers**; tenant snapshot cached per request | Grace/read-only logic goes into the existing filter (D-6). No re-tagging |
| Module codes CORE, PRODUCTION, PROCUREMENT, DEMAND… | Existing codes MODULE_MANUFACTURING, MODULE_DEMAND (procure-to-pay **and** order-to-cash), MODULE_WAREHOUSE (GRN/SRO), MODULE_MIR, MODULE_PROCUREMENT (empty placeholder) | Spec codes mapped to existing ones (D-2) |
| React ModuleProvider / ModuleGuard | Angular 19; menu already gated by `featureCode` from `GET /api/tenant/current` | Angular `ModuleService` + `*smsIfModule` directive (D-15) |
| Hangfire MRP, Demand Forecast, Reorder Point jobs | **Do not exist.** Real per-tenant jobs: production/delivery sweeps, consignment/freight/exception sweeps, RFQ/quotation expiry, scorecards, invoice overdue, FX revaluation | Retrofit the real jobs (D-9) |
| Product capability flags to add | `IsSaleable`, `IsPurchasable`, `IsStockable`, `IsManufacturable` **exist** on `inventory.Products`; `UpdatedDate` exists | Only `IsServiceable` (derived) + 2 service fields added (D-10) |
| `material.ProductProductionSettings`, `service.ProductServiceSettings` extension tables | A36 put service fields on Product two days ago; production settings live on Product (SupplyMethod, DefaultProductionWarehouse), A34 lead times, active BOM | No new tables; API exposes them as conditional nested objects (D-10) |
| BOM in `material.BillOfMaterials` → `ALTER SCHEMA TRANSFER` to inventory | `material.bill_of_materials` owned by MaterialDbContext; A36 already opens `/api/boms` for Manufacturing **or** Services | **No physical transfer** (D-11) |
| `inventory.Routes` + `ProductRoutes` | A33/A34 `logistics.fulfillment_routes` (per org, category STOCK/MANUFACTURE) + variant default route + SO-line override | Make the existing routes module-aware (D-12). No new tables |
| `customers.Customers` new schema | Customers are `suppliers.BusinessPartners` with `IsCustomer` — used by sale orders, invoices, receivables, QuickBooks sync | Customer Master = facade over BusinessPartners (D-13) |
| `workflow.ApprovalRules.entity_type` | `workflow_schema` WorkflowDefinitions keyed by `InterfaceCode` (PR, PO, GRN, MIR…) | Module derived from InterfaceCode in code (D-14) |
| Permission codes `production.%` etc. | UPPER_SNAKE codes (`BOM_VIEW`, `SERVICE_ORDER_EDIT`, `FULFILLMENT_ROUTE_MANAGE`…) | `ModuleCode` column backfilled from a prefix map (D-14); BOM/route perms already exist |
| SQL triggers for `modified_at` | EF Core 8 uses `OUTPUT` on SaveChanges, which **fails on tables with triggers** unless every entity is re-mapped; startup migrates shared SMSGlobal | No triggers — `ModifiedAt` set by the app (D-16) |

## Part B — decisions (adopted defaults)

- **D-1 One registry.** `FeatureDefinitions` *is* the module/feature catalog. New columns: `ParentModuleCode` (null for modules), `IsAlwaysOn`, `IsAvailable`, `Icon`. Dependencies move from the static list to a seeded table `tenant.FeatureDependencies (FeatureCode, DependsOnCode)` — still reconciled from code at startup (code stays the source of truth, the table makes it queryable).
- **D-2 Module mapping** (spec → existing): CORE → MODULE_MASTER_DATA + MODULE_WORKFLOW_ENGINE (+ user/role screens, all IsCore); INVENTORY → MODULE_INVENTORY; FINANCE → MODULE_FINANCE; CUSTOMERS → **new** MODULE_CUSTOMERS; SUPPLIERS → MODULE_SUPPLIERS; PROCUREMENT → MODULE_DEMAND (it already holds requisitions, RFQs, POs — and sale orders, see R-1); WAREHOUSE → MODULE_WAREHOUSE; LOGISTICS → MODULE_LOGISTICS; PRODUCTION → MODULE_MANUFACTURING; SERVICES → MODULE_SERVICES. Spec DEMAND (forecasting/reorder) is **not built** → catalog entry `MODULE_DEMAND_PLANNING`, `IsAvailable=false`. POS, PROJECTS, CRM, MAINTENANCE, ECOMMERCE → `IsAvailable=false` ("Coming soon"). Existing extras stay toggleable: MODULE_MIR, MODULE_REPORTS, MODULE_NOTIFICATIONS, MODULE_INTEGRATION. The empty MODULE_PROCUREMENT placeholder becomes `IsAvailable=false` (hidden in admin). APIs use the existing codes.
- **D-3 Dependencies** (spec §1.4 mapped): DEMAND→(INVENTORY, SUPPLIERS); WAREHOUSE→INVENTORY; LOGISTICS→WAREHOUSE; MANUFACTURING→INVENTORY; SERVICES→INVENTORY; MIR→INVENTORY (existing); INTEGRATION→FINANCE. Cycle check at startup (fails fast).
- **D-4 Licence vs. switch.** Today only the super admin toggles features (= the licence). The spec has the **org admin** enable modules — that would let any Basic org switch on Enterprise modules for free. Adopted: `OrganizationFeatures` gains `IsLicensed` (backfilled = current IsEnabled). Super admin (existing Manage Features page) sets the licence; org admin (new Settings › Modules) can switch a **licensed** module/feature off and on again. Enable on an unlicensed module → 400 "Not included in your plan — contact your administrator". *(Discuss item 1.)*
- **D-5 Always-on.** INVENTORY, CUSTOMERS and the CORE set cannot be switched off by an org admin (MOD-01). FINANCE is marked always-on **only where licensed** — Basic orgs keep Finance off (the spec would hand it to them). *(Discuss item 2.)*
- **D-6 Enforcement & grace** in `FeatureAuthorizationFilter` (snapshot carries per-feature state):
  enabled → pass; disabled + in grace → GET pass, and POST/PUT/PATCH/DELETE pass **only when the route acts on an existing record** (route template has a parameter, e.g. `{uuid}/complete`); creates (POST to the collection) → 403; disabled after grace / never licensed → GET pass only if the org once had it (DisabledAt set), else 403. 403 body: `errorCode: MODULE_NOT_LICENSED`, `module`, `graceEndsAt`. Super admin bypass unchanged.
- **D-7 Grace period**: `DisabledAt`, `DisabledBy`, `GracePeriodEndsAt` (default 30 days, 0–365), `EnabledAt`, `EnabledBy`, `RowVersion` (TS-30) on OrganizationFeatures; CHECK grace⇒disabled. Daily job `ModuleGraceExpiryJob` clears expired grace + history `GRACE_EXPIRED` (MOD-05). Re-enable clears all (MOD-10).
- **D-8 History** `tenant.organization_feature_history` (OrgId, FeatureCode, Action ENABLED|DISABLED|FEATURE_ENABLED|FEATURE_DISABLED|LICENSED|UNLICENSED|GRACE_EXPIRED|AUTO_ENABLED|AUTO_DISABLED, PerformedBy, PerformedAt, GraceDays, Notes). Every change by super admin, org admin or the system is logged (MOD-09).
- **D-9 Jobs.** Shared `IModuleGate.IsEnabledAsync(orgId, code)` (Tenancy implements, cached snapshot). Per-tenant jobs skip orgs without their module: production sweeps → MANUFACTURING; SO delivery sweep, consignment/freight/exception sweeps → LOGISTICS; RFQ link / quotation expiry, reservation sweep → DEMAND; scorecard → SUPPLIERS; invoice overdue, FX revaluation → FINANCE. Allocation and Integration jobs unchanged.
- **D-10 Products.** Existing flags kept. `isServiceable` = ProductType SERVICE (read-only, derived). New columns `ServiceCategory` (GENERAL|INSTALLATION|REPAIR|MAINTENANCE|CONSULTING, service only) and `RequiresSiteVisit`. Product GET adds `productionSettings` (supplyMethod, defaultProductionWarehouse, activeBomUuid, manufacturingLeadTimeDays) **only when MANUFACTURING is enabled** and `serviceSettings` (A36 fields + new two, activeServiceBomUuid) **only when SERVICES is enabled** — key absent otherwise (PRD-CAP-03). Flat fields stay for compatibility. Data never deleted (PRD-CAP-04).
- **D-11 BOM.** Stays in `material.bill_of_materials` — a schema move across two DbContexts on the shared database buys nothing that access rules don't already give (BOM-SHR-01 is about access, met by D-6). New `BomUsage` (UNIVERSAL default | PRODUCTION_PREFERRED | SERVICE_PREFERRED) + `ModifiedAt`. New feature `FEATURE_BOM_MANAGEMENT` (parent INVENTORY): BOM **reads** need only INVENTORY (BOM-SHR-03); create/edit/submit/approve/activate need BOM_MANAGEMENT (BOM-SHR-02). MOD-08: auto-enabled (by system) when MANUFACTURING or SERVICES is enabled; auto-disabled when both off unless an admin enabled it by hand. Existing BOM_* permissions kept (spec's `inventory.bom.*` = BOM_VIEW/CREATE/EDIT/ADMIN). Pickers sort by usage (BOM-SHR-04, advisory).
- **D-12 Routes.** Existing fulfillment routes become module-aware: category MANUFACTURE requires MANUFACTURING (RTE-01). `GET /api/fulfillment-routes` adds `isAvailable` + `unavailableReason`; route pickers hide unavailable ones; the effective-route resolver falls back to the org's default STOCK route when a variant/line route is unavailable (RTE-02) and the SO line shows a warning when none is available (RTE-03). `GET /api/products/{id}/routes` returns each variant's configured/effective route with availability. No product-route table.
- **D-13 Customers** over `suppliers.BusinessPartners` (IsCustomer). New columns: `CustomerType` (WALK_IN|INDIVIDUAL|COMPANY|EMPLOYEE, default COMPANY for existing), `Mobile`, `PaymentTermsDays`, `IsSystem`. Walk-in partner seeded per org (code `C-WALKIN`, IsCustomer, ACTIVE, IsSystem) — cannot be deactivated/deleted/retyped (CUST-01); WALK_IN credit limit must be 0 (CUST-04). New customers created via the customer API get code `C-00001…` per org (CUST-02). `api/customers` facade (list/detail/create/update/status/search/balance); balance = Finance receivables (existing shared lookup). Feature MODULE_CUSTOMERS, always on. Sale orders/invoices keep using partners — same rows.
- **D-14 Cross-module.** `auth.Permissions.ModuleCode` column backfilled by the seeder from a code-prefix map; Role Management groups by module and greys disabled ones (assignable, inert). Workflow: module derived from `InterfaceCode` (PR/RFQ/QUOTATION/PO/SO→DEMAND, GRN/GRN_QC/SRO→WAREHOUSE, MIR*→MIR, INVOICE/PAYMENT→FINANCE, DELIVERY→LOGISTICS, BOM→MANUFACTURING); Workflow Configuration hides/greys definitions of disabled modules. Documents of a disabled module cannot be created (D-6), so a rule is dormant by construction.
  **Maps (REG, one place: `SMS.Shared.Common.ModuleCodeMap`).** Permissions, first matching prefix wins: `MODULES_ SYSTEM_ USER_ AUDIT_ PLATFORM_ LOCATION_ CURRENCY_ ORG_CURRENCY_ FINANCE_SETUP_` → MASTER_DATA (currencies/tax codes are lookups every role reads) · `CUSTOMER_PAYMENT_ CUSTOMER_LEDGER_` → FINANCE, other `CUSTOMER_` → CUSTOMERS · `SUPPLIER_ CONTRACT_` → SUPPLIERS · `RFQ_ PO_ REQUISITION_ SALE_` → DEMAND · `BUDGET_ INVOICE_ PAYMENT_ RECONCILIATION SALES_INVOICE_ PRODUCT_LEDGER_ EXCHANGE_REVALUATION_` → FINANCE · `INVENTORY_ STOCK_ REORDER_ LEAD_TIME_ WAREHOUSE_TRANSFER ALLOCATION_ BOM_` → INVENTORY · `GOODS_RECEIVE PUTAWAY GRN_` → WAREHOUSE · `PICKING DISPATCH DELIVERY_ SHIPMENT_ CARRIER_ RATE_CARD_ SHIPPING_RULE_ FREIGHT_ POD_ FULFILLMENT_ROUTE_` → LOGISTICS · `MATERIAL_` → MIR · `PROD_ MI_ SUPPLY_ QI_ FGR_` → MANUFACTURING · `SERVICE_ORDER_` → SERVICES · `REPORT_` → REPORTS · `WORKFLOW_` → WORKFLOW_ENGINE · `INTEGRATION_` → INTEGRATION. Every code in `PermissionCodes.All` maps (unit-tested). Workflow interfaces: PR, RFQ, RFQ_RESPONSE, QUOTATION, PO, SO, CUSTOMER_PO, SALE_* → DEMAND · GRN, GRN_QC, SRO → WAREHOUSE · MIR* → MIR · INVOICE, PAYMENT, SALES_INVOICE, SUPPLIER_INVOICE → FINANCE · DELIVERY → LOGISTICS · BOM, PRODUCTION_ORDER → MANUFACTURING · SERVICE_ORDER → SERVICES · anything else → none (always enabled).
- **D-15 Frontend** (Angular, SMS Flow kit): `ModuleService` (signals; `isEnabled`, `isFeatureEnabled`, `refresh()`; source `GET /api/tenant/modules/enabled`), structural directive `*smsIfModule`. Settings › Modules page (org admin) per spec §11.3/§15.1 with disable dialog + impact + grace input. Menu: existing gating kept + BOM item gated by FEATURE_BOM_MANAGEMENT + Customers item. Product page sections per §15.2 where they exist today. Customer list/detail pages.
- **D-16 Sync.** `ModifiedAt` (UTC, app-maintained in SaveChanges; backfilled from Created/Updated dates) on Products, ProductVariants, ProductCategories, Warehouses, lookups tax codes / UoMs, BOMs, BusinessPartners. `GET /api/sync/catalog?since=` and `GET /api/sync/customers?since=` (strictly `> since`, capped page). No triggers.
- **D-17 New permissions**: `MODULES_VIEW`, `MODULES_MANAGE` (Org Admin, System Admin); `CUSTOMER_VIEW/CREATE/EDIT/DEACTIVATE` (granted wherever partner view/edit is granted today). Routes/BOM reuse existing codes.
- **D-18 Impact check** (`GET …/{code}/impact`): Shared `IModuleImpactProvider` per module returns in-progress record counts (Material: production orders, service orders; Logistics: open deliveries; Demand: open POs and sale orders); Tenancy aggregates + lists active dependents.
- **D-19 (CUS) Walk-in protections at the save.** CUST-01/04 are enforced in `SuppliersDbContext.SaveChanges` (`CustomerTypes.EnsureInvariants`), not only in the customer API, so `/api/partners` (update/delete) and the legacy `/api/suppliers` status/patch/delete paths cannot delete, deactivate, un-customer or retype the walk-in either. Messages are the contract's; delete says "The walk-in customer cannot be deleted.". A partner saved through any path with `IsCustomer` and no type gets COMPANY (same as the backfill).
- **D-20 (CUS) Walk-in seeding.** Created in `MigrateSuppliersSchema` for every organization (after the guarded migrate; failure logged, never fatal), by an `IOrganizationProvisionedHandler` for new organizations, and lazily by list/search/sync. Code `C-WALKIN`, name "Walk-in Customer", PartnerType CUSTOMER, not a vendor. A partner someone already coded C-WALKIN is left alone (no takeover, no second row). It is sent to QuickBooks like any customer when an invoice names it (harmless: one "Walk-in Customer" per company); it adds 1 to the dashboard's active-customer count.
- **D-21 (CUS) Codes & status.** C-00001… = one past the highest `C-nnnnn` the organization ever used (deleted rows included); a race on the unique (org, code) index is retried (3×). The `IDocumentNumberGenerator` was not used — its format is `PREFIX-YYYY-NNNNN`. New customers are ACTIVE at once (no vendor onboarding). `PATCH …/status` sets `IsActive`; a pure customer's `Status` mirrors it (ACTIVE/INACTIVE), a vendor's `Status` is left to the supplier workflow. PUT is a full replace of the upsert fields (null clears; `paymentTermsDays` null → 0); credit limit follows the gate (D-17 ✔ CREDIT_MANAGEMENT): ignored without it, and a WALK_IN type always gets 0 (a request for more is 400).
- **D-22 (CUS) Balance.** New Shared `ICustomerBalanceLookup` (TryAdd), implemented in Suppliers by `SalesInvoiceCustomerBalanceLookup`, which reads Finance's sales invoices directly (as the supplier scoring already does): sum of open (ISSUED, PARTIALLY_PAID, OVERDUE) `BalanceDue × ExchangeRate` (rate locked at issue, 1 when none) = sale base; `overdue` = the part past `DueDate`; `currencyCode` = the org's sale base code. The customer ledger was not used — its running balance mixes currencies (A29). Unapplied advances/credit notes are not netted. Finance may register its own implementation and it wins.
- **D-23 (CUS) Customer sync.** `GET /api/sync/customers` returns rows with `ModifiedAt > since` ordered by (ModifiedAt, Id), `limit` 1–1000; a page is extended to the end of a run of equal `ModifiedAt` so "since = last modifiedAt" never skips a row (a page can exceed `limit` by the tie). Deactivated and deleted customers are included with `isActive: false` so offline copies drop them.
- **D-24 (CUS) Route takeover.** The A29 `CustomersAliasController` (`GET api/customers`, ungated, `BusinessPartnerModel[]`, used by no screen) is removed; `CustomersController` owns `api/customers`. Its ratchet entry was removed from `UngatedEndpointsRatchetTests`.
- **D-25 (OPSB) Job gate mechanics (D-9).** One Shared helper, `ModuleGateExtensions` (`IsOnAsync`, `SkippedAmongAsync`, `RunForEnabledOrganizationsAsync`); `IModuleGate` is an optional constructor parameter everywhere — no gate registered ⇒ every module on (behaviour unchanged). Skips log at Debug. Batch sweeps (SO delivery/production sweeps, Material production-delivery sweep, tracking poll, invoice overdue) exclude skipped organizations **in the query**, so a switched-off organization's backlog never fills a batch and starves the others. A skipped organization's pending work **stays pending** and resumes when the module is back (A34's "stop waiting" is kept only for the snapshot path without a gate). Sweeps that go through the EF tenant filter (freight accrual, delivery exception, supplier scorecard) run once unscoped as before when every organization has the module, else once per enabled organization under `HangfireTenantScope`. The booking sweep's lease expiry is ledger housekeeping and stays global. `RfqLinkExpiryJob` now reads with `IgnoreQueryFilters` explicitly.
- **D-26 (OPSB) Route availability (D-12, RTE-01..03).** Single source: Logistics' `IFulfillmentRouteLookup` sets `FulfillmentRouteSummary.IsAvailable/UnavailableReason` (Shared `FulfillmentRouteAvailability`: module gate first — grace = off — else tenant snapshot, else on). Route list/detail add `isAvailable` + `unavailableReason` ("Manufacturing is switched off"). Creating a MANUFACTURE route or changing a route's category to MANUFACTURE while off → 400 "Manufacturing is switched off for your organization."; an existing MANUFACTURE route can still be renamed/activated. SO line override with an unavailable route → 400 "Line n: 'CODE' — Manufacturing is switched off for your organization.". Resolver: an unavailable line/variant route falls back to the org default for the order's delivery mode (never MANUFACTURE, A34 D-6), `routeSource` ORG_DEFAULT and `routeWarning` on the SO line and the delivery-preview line; no default ⇒ ROUTE_MISSING blocker plus the warning. Confirm therefore snapshots the stock fallback and raises no production order. Confirmed lines keep their snapshot (no warning).
- **D-27 (OPSB) `GET /api/products/{id}/routes`.** Served by Logistics (`ProductRoutesController`, MODULE_LOGISTICS, FULFILLMENT_ROUTE_VIEW/MANAGE/ASSIGN) for both `{id:int}` (as the other product routes) and `{uuid:guid}`. Variants come from a new Shared `IProductVariantRoutes` (implemented in Inventory by OPSA, D-35); a host without it answers 404. Effective route = the configured one when available, else the organization's SHIP default (a product has no order mode); `warning` when the configured route is unavailable or nothing applies.
- **D-28 (OPSB) Impact counts (D-18).** Logistics: deliveries not DELIVERED/CLOSED/SHORT_CLOSED/CANCELLED ("Open deliveries"), consignments not DELIVERED/RETURNED_TO_ORIGIN/CANCELLED/LOST ("Open consignments"). Demand: purchase orders not CLOSED/CANCELLED/REJECTED ("Open purchase orders"), sale orders not INVOICED/CLOSED/CANCELLED, drafts included ("Open sale orders").
- **D-29 (OPSB) Sub-feature gates placed.** FEATURE_RFQ_MANAGEMENT on `QuotationsController` (`api/quotations`, the internal RFQ screens) — the anonymous supplier portal `api/public/rfq-portal` is untouched, so already-sent links keep working. FEATURE_PICK_LISTS on `PickListsController`. FEATURE_SHIPMENT_TRACKING on the whole `ConsignmentsController` (contract: "consignments") and `TrackingLinksController`; the anonymous carrier webhooks and public tracking page are not gated (carriers push regardless; both already check the organization). FEATURE_PURCHASE_RETURNS on Warehouse `SrosController`. Deliveries untouched.
- **D-30 (OPSA) Product module blocks (D-10).** `productionSettings` / `serviceSettings` are decided by `IModuleGate` for the caller's organization (the product's own when the caller has none, e.g. super admin); no gate registered ⇒ both present; grace ⇒ absent (gate semantics). Omitted via `[JsonIgnore(WhenWritingNull)]` on those two properties only. `manufacturingLeadTimeDays` = the default variant's A34 override, else `Product.LeadTimeDays` for a MANUFACTURE product, else null (stored data, not the full calculator). `activeBomUuid/Number` = the default variant's active BOM, else any variant's; `activeServiceBomUuid` only for a SERVICE with `hasServiceBom`. One `IBomStructureReader` call serves both blocks and A36's `hasActiveServiceBom`, made only when a BOM can matter. `ServiceCategory`/`RequiresSiteVisit` follow the A36 rules (create and PATCH; omitted = unchanged, explicit null clears; refused on non-services: "Service category is only applicable to service products" / "Site visit is only applicable to service products"; cleared when the type leaves SERVICE; unknown code 400). Codes in Shared `ServiceCategory`.
- **D-31 (OPSA) BOM usage & gates (D-11).** `bomUsage` on create/update (DRAFT/REJECTED, as every edit) and on new **`PUT /api/boms/{uuid}/usage {bomUsage}`** (BOM_EDIT + BOM_MANAGEMENT) for any status but OBSOLETE — the contract's "editable in any non-terminal status" without loosening the immutable-recipe rule. A new version copies it. `?preferFor=PRODUCTION|SERVICE`: matching usage, then UNIVERSAL, then the other, then the old order (UpdatedAt desc); anything else 400. List, detail and versions carry `bomUsage`; list/detail carry `modifiedAt`. `BomsController`: class gate MODULE_INVENTORY (replaces A36's MANUFACTURING-or-SERVICES), every write action FEATURE_BOM_MANAGEMENT. `QualityInspectionsController`: MODULE_MANUFACTURING + FEATURE_QUALITY_INSPECTION, both class-level. Production/service-order BOM selection (ActiveBomResolver) is untouched.
- **D-32 (OPSA) ModifiedAt mechanics (D-16).** Shared `IHasModifiedAt` + `DbContext.StampModifiedAt()` (Added/Modified, one UTC instant per save; reusable by CUS) in Inventory, Material and Lookups contexts. Backfill: Products `COALESCE(UpdatedDate, CreatedDate)`, variants/categories/warehouses `CreatedDate`, BOM header and lines the header's `UpdatedAt`; new rows written outside EF get `DEFAULT SYSUTCDATETIME()`; the bulk route assign (ExecuteUpdate) sets it itself. A change to BOM lines alone moves the lines' ModifiedAt, not the header's. **Lookups**: tax codes and UoMs are `lookups.LookupValues` rows of type `tax-code` / `uom`, so the column is on LookupValues (existing rows = time of the change). Lookups never runs migrations at startup, so `LookupsDataSeeder` applies the same guarded SQL on every start (the migration carries it for `dotnet ef`); the old `IX_LookupValues_TypeId` is kept.
- **D-33 (OPSA) Catalog sync (§6).** `GET /api/sync/catalog` (MODULE_INVENTORY + INVENTORY_VIEW): per collection `ModifiedAt > since` oldest first, `limit` 1–1000 (default 500), a page extended over a run of equal ModifiedAt (as D-23), deactivated rows included. Additive field **`nextSince`**: the earliest last-modifiedAt among the collections that were cut, else `serverTime` (rows already received may repeat; upsert by id). `taxCodes`/`uoms` through new Shared `ISyncLookupReader` (Lookups implements; empty without it). Hard deletes (a never-transacted variant, a category) are not reported.
- **D-34 (OPSA) Material impact (D-18).** One line per non-terminal status with a count: "Production orders – In progress", "Service orders – Waiting" … (organization explicit, tenant filter bypassed).
- **D-35 (OPSA) OPSB's Inventory needs (D-26/D-27).** Inventory implements Shared `IProductVariantRoutes` (active variants, product-page order, null for another organization's product); single and bulk variant route assignment refuse a route Logistics reports `!IsAvailable` with `FulfillmentRouteAvailability.ManufacturingOffMessage`.
- **D-36 (REG) Catalog-only sub-features.** §1.3 "(n/a)" entries with no screen at all (BLANKET_ORDERS, CARRIER_INTEGRATION, MRP_SCHEDULING, PRODUCTION_COSTING, WORK_CENTERS, FIELD_SERVICE, SERVICE_CONTRACTS, BANK_RECONCILIATION, LOYALTY_PROGRAM) are `IsAvailable=false` ("Coming soon", in no plan, cannot be enabled). PRODUCT_VARIANTS is **core** (every product is stocked through variants). STOCK_TRANSFERS, STOCK_COUNTS, MULTI_CURRENCY are toggleable but not enforced (R-2). MODULE_PROCUREMENT is unavailable and hidden (never listed to org admins; old rows kept). Plan defaults: an unavailable entry never; a sub-feature only with its parent in the plan; BOM_MANAGEMENT with MANUFACTURING or SERVICES (Basic has none). Existing exclusions kept — FEATURE_EMAIL_NOTIFICATIONS is now under NOTIFICATIONS, so Basic orgs (Notifications off) no longer list it as usable (it gates nothing today).
- **D-37 (REG) Backfill of new rows for existing orgs.** A new top-level entry follows the org's plan template (MODULE_CUSTOMERS is in every plan → licensed + on for every org incl. Basic). A new sub-feature follows what the org has **now**: licensed/on with its module (a Basic org given Logistics by hand gets PICK_LISTS); BOM_MANAGEMENT on (system-managed) when MANUFACTURING or SERVICES is on. Existing rows: the migration sets `IsLicensed = IsEnabled` once, when it creates the column; the DB default of IsLicensed is 1 only so a row written by an older API build on the shared database is licensed (EF always writes the value).
- **D-38 (REG) "Usable" and "once had".** Usable = available AND licensed AND on AND (sub-feature) its module usable; `TenantSnapshot.EnabledFeatureCodes`, `IModuleGate`, `GET api/tenant/current` (`enabledFeatureCodes`) and `/modules/enabled` all read it — so `tenant/current` no longer lists a feature whose module is off, or a module in grace. "Once had" (D-6 reads) = `DisabledAt` set: every switch-off (org admin, super-admin unlicense, system) sets it, a switch-on clears it. Grace exists only while licensed (unlicensing ends it). An expired grace reads as read-only in the filter at once; the daily job (00:15 UTC, `tenant.module-grace-expiry`) tidies the row and logs GRACE_EXPIRED. `IModuleGate` answers false for an inactive organization.
- **D-39 (REG) Filter details.** "Acts on an existing record" = the matched route has a value other than controller/action/area/page (so `POST {id}/lines` passes during grace, `POST api/x` does not). HEAD/OPTIONS are reads. Several `[RequiresFeature]` = all must pass; the refusal names the **blocking** code — the parent module when that is what is off (a FEATURE_PICK_LISTS endpoint while Logistics is in grace answers `module: MODULE_LOGISTICS` + its graceEndsAt). The 403 is written by the filter as the action result (`ModuleNotEnabledResponse`); `GlobalExceptionMiddleware` and every other 403 are unchanged.
- **D-40 (REG) Org-admin semantics.** Enable/disable/feature calls are idempotent (already in that state → the card, no history). Disable refuses always-on and core modules, then checks grace, then enabled dependents. Dependencies/dependents count only usable ones (a dependent in grace does not block). Feature toggle: unavailable / unlicensed / core-off / module-off refusals per §1.1; features have no grace; a feature switched by hand stops being system-managed. MOD-08: switching MANUFACTURING or SERVICES on auto-enables (and licenses) BOM_MANAGEMENT when off; with both off a **system-managed** BOM_MANAGEMENT is auto-disabled with the driving module's grace end; one switched on by hand stays. The super-admin licence path runs the same rule. System history rows have `PerformedBy` null ("System").
- **D-41 (REG) RowVersion.** The card's `rowVersion` is the module row's; any feature change also touches the module row, so it moves with its features. A supplied stale value → 409 before anything changes; a race after the read → 409 via the EF concurrency token. Omitted → no check.
- **D-42 (REG) Super admin.** Route stays `api/system/organizations/{id}/features` (the contract's `api/organizations/...` is shorthand); history at `GET api/system/organizations/{id}/features/history` (all codes, `featureCode` always set). Toggle on = licensed AND on (re-enables a module an org admin switched off, clears grace); off = unlicensed AND off; enabling a "Coming soon" entry is refused. `apply-plan-template` resets the licence the same way and logs it. Org creation writes licence = plan, no history rows.
- **D-43 (REG) Grants & permission lists.** MODULES_VIEW/MANAGE reach System Admin and Org Admin through their `PermissionCodes.All` grants. CUSTOMER_VIEW/CREATE/EDIT/DEACTIVATE are added on every start to every role (built-in or custom) allowed SUPPLIER_VIEW/CREATE/EDIT/MANAGE respectively — only missing grants; one an administrator switched off stays off (A35 pattern). `GET api/roles/{id}` items and the role/user permission lists add `moduleCode` (stored column, map fallback) and `moduleEnabled` (caller's org for roles, the target user's org for user permissions). Workflow: `GET api/workflow/definitions` items (per row's org) and `GET api/workflow/config/interfaces` rows (caller's org) add `moduleCode` / `moduleEnabled`.

## Residuals
- R-1 Sale orders, inquiries and quotations are gated by MODULE_DEMAND (= Procurement); switching Procurement off also switches selling off. Splitting needs a new MODULE_SALES and re-gating ~6 controllers — not in the register.
- R-2 Spec sub-features without a real screen (BLANKET_ORDERS, BARCODE_SCANNING, WORK_CENTERS, MRP_SCHEDULING…) are catalog entries only; only features mapped to real endpoints/menus are enforced (list in API-CONTRACT §1.3).
- R-3 Spec jobs (MRP, forecast, reorder) do not exist; TS-037-12/32 are tested against the real Manufacturing sweep job.
- R-4 (OPSA) The sync's `taxCodes` are the legacy `tax-code` lookup values; the tax codes documents actually use are Finance's `finance.tax_codes` (SAP S-1). Sending those needs a Finance reader (Finance owner).
- R-5 (QA) Read access after switch-off has no end: an org whose module was disabled **or unlicensed by the super admin** keeps GET access to that module's records indefinitely (D-6 "data is permanent"). A licence-removal cut-off would need a separate rule.
- R-6 (QA) A sub-feature switched off by the org admin is read-only, not hidden from the API (GETs still answer; writes 403). The menu hides it.
- R-7 (QA) During grace, a POST on a route naming an existing record passes even when it creates a child document (pick list for a delivery, QI for a production order) — D-39 as designed.
- R-8 (QA) With the module gate in the host, the A34 MANUFACTURING_DISABLED confirm blocker can no longer fire (lines fall back instead, D-26); the variant-assign refusal uses the generic D-35 message without the route code.
- R-9 (COORD) The Sales menu group's Demand gate moved onto its items so the always-on Customers item stays visible without Demand; the Tracking menu group is not gated by FEATURE_SHIPMENT_TRACKING (only consignments/tracking links are).
