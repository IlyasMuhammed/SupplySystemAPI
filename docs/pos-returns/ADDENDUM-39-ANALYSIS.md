# Addendum 39 — POS Returns, Exchanges & Store Credit: reality check & decisions

Spec: SMS-FSD-ADD-039 v1.0 (C1–C12) · Register: 268 items · Contract: [API-CONTRACT.md](API-CONTRACT.md) · Tasks: [ADDENDUM-39-TASKS.md](ADDENDUM-39-TASKS.md) · Builds on [A38](../pos/ADDENDUM-38-ANALYSIS.md).
Status 2026-10-11: defaults below ADOPTED (user: "perform the tasks") — overridable.

## Part A — spec vs. what A38 built

| Spec assumes | Reality after A38 | Consequence |
|---|---|---|
| Returns are new; `returned_qty` to add on lines | A38 already has RETURN orders (RET- numbers), `PosOrderLine.ReturnedQuantity`, PARTIALLY_RETURNED / RETURNED statuses, remainder refund rule, `POST /orders/{uuid}/return`, FEATURE_POS_RETURNS, POS_RETURN stock, Finance credit note (SalesInvoice status CREDIT_NOTE, `SCN-`) + `customer_refunds` | **Extend** the A38 return path (D-1); no `returned_qty` migration |
| "Credit note" = store credit voucher | Finance already uses "credit note" for the customer AR credit (SCN-). Two different things | POS store credit is its own `pos.store_credit_notes` (numbers `CN-…`); UI says **"Store credit"**; permission codes keep the spec names (D-2) |
| Journal entries (revenue, tax, cash, CN liability, restocking income, inter-store receivable/payable) | No GL (A38 D-8). Money = SalesInvoice / credit note / payments / refunds; QuickBooks does GL | Store credit and exchange become **tender methods** in Finance (D-3); store-credit liability = Σ active balances (report); no account mapping (C11 mapped, GL ✕) |
| Restocking fee income | No other-income ledger | Fee is retained revenue: the Finance credit note credits the return **less** the fee (D-5) |
| Cross-store inter-store JE pair | Stores are not separate ledgers; Finance is per organization | Cross-store return = normal credit note on the original invoice; stock into the processing store; refund in the processing store's shift; weekly **cross-store report** instead of JEs (D-7) |
| `customers.Customers` bigint FK | BusinessPartner UUID (A37) | Guid refs |
| Exchange = one order with mixed lines + one JE | One POS order (type EXCHANGE) is fine; Finance needs a credit note (return part) + a sale invoice (new part) | Linked by an internal EXCHANGE tender pair (D-6) |
| SQL view `vw_ReturnableOrderLines`, triggers, FK to auth.Users | EF queries, app ModifiedAt, Guid/int refs | ✕ view (same data via API #11) |
| Dotted permissions | UPPER_SNAKE (A38 D-13) | D-9 |
| Manager PIN at the till | A38 PIN infrastructure (store staff, IPosPinService, offline hashes) | Authorization token (online) / offline-verified PIN flag (D-8) |

## Part B — decisions

- **D-1 Return path.** The A38 endpoint `POST api/pos/orders/{uuid}/return` is enriched (reason, policy, authorization, restocking fee, store credit, cross-store) — not duplicated. A38 refund-remainder rule stays. Offline same-store returns arrive through `POST api/pos/returns/sync` (idempotent on localId, same validation, flags instead of refusals where the cashier already acted offline: `POLICY_OVERRIDDEN_OFFLINE`).
- **D-2 Store credit** = `pos.store_credit_notes` + `pos.store_credit_transactions` (ISSUE/REDEEM/EXPIRE/CANCEL/ADJUST), statuses ACTIVE / FULLY_REDEEMED / EXPIRED / CANCELLED, number `CN-{store}-{yyyyMMdd}-{seq:0000}` (offline `CN-{store}-OFF-{short}`), optional customer (null = bearer), optional expiry from policy. Redemption online only, capped at min(balance, order remaining), no change. Feature `FEATURE_POS_CREDIT_NOTES`.
- **D-3 Finance mapping.** New customer payment/refund methods `STORE_CREDIT` and `EXCHANGE` (no cash movement). Return refunded as store credit → Finance credit note + refund method STORE_CREDIT; sale paid by store credit → payment method STORE_CREDIT. Customer ledger stays balanced per partner; the outstanding store-credit liability is the POS subledger (Σ active balances; credit-note report + shift totals).
- **D-4 Policies & reasons** in the POS module. Org default policy and the 9 reasons are seeded per organization lazily (first read) and when POS is licensed — never by a startup data migration on SMSGlobal. Resolution: active store policy → active org default → refuse "No return policy configured". `Store.ReturnPolicyId` ✕ (redundant with the store-policy unique index).
- **D-5 Restocking fee** = round(return total (incl. tax) × fee% / 100), reason override wins, 0 waives (matches FSD §12.2, TS-23). Refund = return total − fee. Finance credit note lines are the returned lines scaled by (1 − fee/total) (tax scaled too); product ledger still takes the full quantity back at original cost.
- **D-6 Exchange** = one POS order `EXCHANGE` (negative return lines + positive new lines). Postings: Finance credit note for the return part with refund tender `EXCHANGE` (= return value − fee), Finance counter sale for the new part paid by tender `EXCHANGE` (same amount, capped at the new total) + the net tenders; net < 0 → the remainder is refunded via the chosen refund method on the credit note. Stock POS_RETURN in + POS_SALE out. Exchange window = `exchange_window_days ?? return_window_days`, 0 = no exchanges.
- **D-7 Cross-store** (FEATURE_POS_CROSS_STORE_RETURNS + POS_RETURN_CROSS_STORE): online only; processing store's policy must accept; manager authorization when the policy says; the **original store's** effective policy window applies; stock IN to the processing store's warehouse; refund counted in the processing shift. `CrossStoreReconciliationReport` (weekly) = per store pair, amounts returned at B for sales of A → notification to users holding POS_RETURN_REPORTS.
- **D-8 Manager authorization.** Online: `POST api/pos/returns/authorize {terminalUuid, managerUserId?, pin, originalOrderUuid, amount, reasons[]}` → one-time token (5 min, bound to order + amount ceiling + manager); the return request carries it; `authorized_by/at` recorded. Manager = store staff SUPERVISOR with POS_RETURN_OVERRIDE (or POS_RETURN_CROSS_STORE for a cross-store need). Offline: PIN checked on the device against cached hashes; the synced order carries `authorizedByUserId` + flag `AUTHORIZED_OFFLINE`, server checks that user's role/permissions at sync and flags `AUTHORIZATION_INVALID` (never rejects a completed offline return).
- **D-9 Permissions** `POS_RETURN_CROSS_STORE POS_RETURN_OVERRIDE POS_RETURN_POLICY_MANAGE POS_RETURN_REASON_MANAGE POS_RETURN_REPORTS POS_CREDIT_NOTE_ISSUE POS_CREDIT_NOTE_REDEEM POS_CREDIT_NOTE_CANCEL POS_CREDIT_NOTE_VIEW POS_CREDIT_NOTE_REPORTS`; role grants per spec §16.2 (cashier: redeem; supervisor: cross-store, reports, issue, redeem, view; store manager: + override, cancel, CN reports; admins all).
- **D-10 Shifts.** `TotalStoreCreditIssued`, `TotalStoreCreditRedeemed` (recomputed like other totals); expected cash unchanged; refund methods recorded in the processing shift.
- **D-11 Events & jobs.** Hub: ReturnProcessed, CreditNoteIssued, CreditNoteRedeemed, CreditNoteExpired, ReturnPolicyChanged (store groups). Jobs: `StoreCreditExpiryJob` daily 00:30 UTC; `CrossStoreReconciliationReport` weekly Mon 06:00 UTC.
- **D-12 QuickBooks.** Credit notes, refunds and payments still don't sync (A38 R-2); STORE_CREDIT/EXCHANGE are internal and never sync.
- **D-13 (XFIN) Finance tender methods.** `CustomerPaymentMethods.StoreCredit`/`Exchange` (`STORE_CREDIT`, `EXCHANGE`; columns are nvarchar(20), **no migration**). `ICounterSaleService` maps POS `STORE_CREDIT`/`EXCHANGE` 1:1: a sale tender → `CustomerPayment` of that method, allocated and ledgered (PAYMENT credit) exactly like cash; a return/exchange refund → `CustomerRefund` of that method (REFUND debit). The tender `reference` is kept as `BankReference` / refund `Reference` — POSR should pass the store-credit number (`CN-…`). The back office **cannot key** them (`POST customer-payments` → 400 "recorded by the POS only"); the payment list filter accepts them (`?method=STORE_CREDIT|EXCHANGE`), so a `?method=CASH` list never contains them. A **void** of a sale paid partly by store credit reverses that payment like the others (D-38) — POSR must put the value back on the store-credit note itself.
- **D-14 (XFIN) No cash report to correct.** Verified: nothing in Reports or Finance sums customer payments/refunds by method or as cash (R2 statement is ledger-driven, R3 aging reads allocations — store credit/exchange settle receivables correctly there; Reports' payment summary is supplier payments; no dashboard reads customer payments). The POS shift expected-cash is POSR's (D-10). QuickBooks: no payment/refund publisher exists (only invoices, bills, partners, variants) — STORE_CREDIT/EXCHANGE can never reach it.
- **D-15 (XFIN) Scaled credit notes (D-5) need no change.** `PostReturnAsync` stores line amounts as given and only caps them (per original line: Σ qty ≤ sold, Σ LineTotal ≤ sold LineTotal; LineTotal = Net + Tax); there is no pro-rata check. RETURN_IN takes the **full** returned quantity at the sale's unit cost; the retained fee stays in revenue (R4/R8/profitability subtract only the credited net). Consequence for POSR: because Finance's per-line cap is on credited amounts, a later remainder-rule return of the same line still fits (credited < sold). Tested with a 10% fee.
- **D-16 (XFIN) Permissions, roles, features.** 10 codes in `PermissionCodes` (+ All, seeded with names/descriptions, module POS via the `POS_` prefix). Grants: POS_CASHIER + CREDIT_NOTE_REDEEM; POS_SUPERVISOR + RETURN_CROSS_STORE, RETURN_REPORTS, CREDIT_NOTE_ISSUE, CREDIT_NOTE_VIEW (redeem inherited); STORE_MANAGER + RETURN_OVERRIDE, CREDIT_NOTE_CANCEL, CREDIT_NOTE_REPORTS; SYSTEM_ADMIN/ORG_ADMIN via All; POLICY_MANAGE / REASON_MANAGE are admin-only. The seeder adds only missing (role, permission) rows, so a grant switched off in the role editor (IsAllowed=false) stays off. Tenancy: `FEATURE_POS_CREDIT_NOTES` "Store Credit" and `FEATURE_POS_CROSS_STORE_RETURNS` "Cross-Store Returns", toggleable sub-features of MODULE_POS; new Standard/Enterprise orgs get them with POS; existing orgs through the A37 sub-feature backfill (licensed/on exactly as their MODULE_POS row; orgs without POS get unlicensed, off rows). No Auth/Tenancy migration (seed data only). The A38 E2E assertions on POS permission counts/role grants (`PosE2ETests`) were updated to 27 codes.

- **D-17 (POSR) One return path, A38 shape still accepted.** `orders/{uuid}/return`, `orders/{uuid}/exchange` and `returns/sync` run the same code (`PosOrderService.Returns.cs`). A39 clients send `reasonUuid` + `refundMethod`; the A38 body (`reason` text + `refunds[]`) still works (no reason row, policy rules still apply). The A38 refusal texts were replaced by the A39 §0 ones (`Only sales can be returned.`, `Cannot return a voided order.`, `All items in this order have already been returned.`, `Cannot return {q} of '{name}'. Only {r} returnable.`). Processing shift = `shiftUuid`, else the OPEN shift of `terminalUuid`, else of the original terminal; the processing store is that shift's store — a different store ⇒ cross-store (no longer refused as in A38).
- **D-18 (POSR) Seed values (D-4).** Reasons (sortOrder 10…90; fee override in brackets): DEFECTIVE (0), WRONG_ITEM (0), WRONG_SIZE, NOT_AS_EXPECTED (note), CHANGED_MIND, DUPLICATE (RETURN only, 0), PRICE_MATCH (RETURN only, note+manager, 0), WARRANTY (note+manager, 0), OTHER (note). Org default policy "Organization default": return window 30, exchange window null (= 30), requireReceipt, no no-receipt exchange, cross-store allowed without manager, fee 0, no amount ceiling, refund to any method, cash and store credit allowed, store credit expiry 365 days. Seeded on first read of reasons/policies/lookup/return and on standalone issue; a concurrent seeder loses quietly on the unique indexes.
- **D-19 (POSR) Which policy decides what.** Window (POS-XST-06): the ORIGINAL store's effective policy; days = store-local date of the return (offline: `createdAtLocal`) − store-local date of the sale (original store's timezone); null = no limit; expired when days > window. Exchange window = `exchangeWindowDays ?? returnWindowDays` of the original store; "exchanges allowed" (≠ 0), cross-store acceptance + manager, restocking fee, `maxReturnNoAuth`, refund-method rules and store credit expiry: the PROCESSING store's policy. The lookup's `policy` is the processing store's EffectivePolicy with `returnWindowDays`/`exchangeWindowDays` replaced by the original store's (so the window fields the till shows are the ones applied).
- **D-20 (POSR) Amounts.** RETURN lines keep the A38 remainder-rule amounts (unscaled); `restockingFeeAmount` = round(Σ line totals × fee% / 100, away from zero); RETURN `grandTotal` = the refund (Σ line totals − fee), so shift `netTotal` keeps the fee. The Finance credit note gets the lines scaled by refund/total, remainder on the last line (D-15 confirms Finance accepts it). A 100 % fee leaves nothing to refund: no Finance credit note is posted (financePosted true, stock still comes back) — R-5.
- **D-21 (POSR) Manager authorization.** Token = 32 random bytes (base64url) given once; only its SHA-256 (hex) is stored in `pos.return_authorizations` with the original order, terminal, manager, amount ceiling (compared with the refund value = return total − fee), 5-minute expiry and whether the manager held POS_RETURN_OVERRIDE / POS_RETURN_CROSS_STORE at issue. `UsedAt` is a concurrency token: two returns with one token ⇒ one wins, the other 409. Manager = active SUPERVISOR staff (store_staff role) of the terminal's store; `reasons` in the authorize body only matter when it is exactly `[CROSS_STORE]` (then POS_RETURN_CROSS_STORE suffices, else POS_RETURN_OVERRIDE is required — re-checked at use). Only a wrong PIN counts toward the shared terminal lockout. Missing token ⇒ `"Return window expired ({n} days)."` when WINDOW is among the needs, else `"Manager authorization required."`; bad/used/expired token ⇒ `"The manager authorization is invalid or has expired."`; over the ceiling ⇒ `"The refund exceeds the amount the manager authorized."`; manager lacking the permission for the needs ⇒ `"This manager cannot authorize this return."` — all 400 with `result: { requiresManager: true, reasons }`.
- **D-22 (POSR) Refund methods.** `refundToOriginalMethod` ⇒ the original's non-cash method with the largest net amount (ON_ACCOUNT and STORE_CREDIT included), else CASH. STORE_CREDIT also needs FEATURE_POS_CREDIT_NOTES (else the policy message). Refunding as store credit needs no POS_CREDIT_NOTE_ISSUE (the policy governs it); the standalone issue does. EXCHANGE is never a client method (server-made tender only).
- **D-23 (POSR) Exchange.** Number `EXC-{store}-{yyyyMMdd}-{seq:0000}`. Return lines stored negative (quantity, net, tax, total, discount), new lines positive with the processing store's tax; `grandTotal` = new total − return total, `netAmount` = grandTotal + fee, `settlement` PAY/EVEN/REFUND. Payments: EXCHANGE refund + EXCHANGE tender of min(return value, new total) (reference = the EXC number), then the refund method for a negative net, or the client's payments for a positive one (STORE_CREDIT online only, ON_ACCOUNT with the A38 credit rules, change on cash). Finance: credit note on the exchange uuid, sale on `MD5(uuid + "EXCHANGE_SALE")`; stock POS_RETURN (returned items) + POS_SALE (new items) on the exchange uuid. Discounts on new lines need POS_ORDER_DISCOUNT of the caller. An exchange cannot be voided. Earlier returns/exchanges are counted by absolute value for the remainder rule.
- **D-24 (POSR) Store credit.** Number `CN-{store}-{yyyyMMdd}-{seq:0000}` (store sequence, prefix CN); an offline issue keeps the device's `CN-…-OFF-…` as `offlineNumber` (lookup finds either). Expiry = return time + policy days; standalone: `expiresAt` ?? policy days. Redemption (sale or exchange tender): online only (also enforced for orders pushed `isOffline:true`), FEATURE_POS_CREDIT_NOTES + POS_CREDIT_NOTE_REDEEM of the caller, ACTIVE and unexpired, bound customer must match, Σ per note ≤ balance, ≤ the order's remaining (tender check). The spend is saved with the order (note RowVersion + `CK_store_credit_notes_Balance >= 0`): a concurrent second spend answers 409 `"The credit note was used at the same time…"`. Tender/refund `reference` = the CN number (XFIN D-13). Void of a sale paid by store credit ⇒ ADJUST +amount, FULLY_REDEEMED → ACTIVE (XFIN request). Cancel only ACTIVE (CANCEL −balance). A note past its expiry reads EXPIRED (and is refused) before the nightly job books it. `redeemedAmount` = −Σ REDEEM − Σ ADJUST.
- **D-25 (POSR) Offline sync.** Refused offline as online: cross-store, store-credit redemption, malformed/unknown data, ON_ACCOUNT rules, quantities beyond what is returnable. Flagged instead (`POLICY_OVERRIDDEN_OFFLINE` + warning): expired window or other manager need without an authorizer, exchanges not allowed, refund method against policy. `authorizedByUserId` ⇒ `AUTHORIZED_OFFLINE`, + `AUTHORIZATION_INVALID` when that user is not active SUPERVISOR staff of the store holding the needed permission. A closed shift takes the offline return late (warning + `System:` note). Idempotent on `localId` (same kind + original ⇒ the stored order; else 409).
- **D-26 (POSR) Shift & hub.** `totalStoreCreditIssued` = STORE_CREDIT refunds of the shift (standalone issues belong to no shift); `totalStoreCreditRedeemed` = STORE_CREDIT tenders of non-voided sales/exchanges; STORE_CREDIT and EXCHANGE refunds are no longer in `totalOtherRefunds`; exchanges count in `orderCount` and `refundCount`, `grossTotal` += their new part, `netTotal` −= their return part after the fee. `ReturnProcessed.refundMethod` = the single refund method, `EXCHANGE` when nothing was paid out, `MIXED` for an A38 multi-tender refund. Policy changes push `ReturnPolicyChanged` to the store (store override) or every active store (default).
- **D-27 (POSR) Jobs.** `StoreCreditExpiryJob` (00:30 UTC) per org with MODULE_POS **and** FEATURE_POS_CREDIT_NOTES, in its tenant scope; EXPIRE transaction by user 0 (system). `CrossStoreReconciliationReport` (Mon 06:00 UTC, last 7 days by `createdAt`) per org with MODULE_POS: one notification `POS_CROSS_STORE_REPORT` (entity PosOrder, link `/portal/pages/pos/orders?orderType=RETURN,EXCHANGE`) listing "sold at A → returned at B: n return(s), amount" to every active user holding POS_RETURN_REPORTS among the org's store staff plus `IPosPinService.SearchUsersAsync` (≤ 100 users) — never a role broadcast.

## Residuals
- R-1 No GL: restocking-fee income, store-credit liability and inter-store balances are reports, not ledger accounts (C11).
- R-2 Bearer store credit redeemed by another customer moves value between customer ledgers (each balanced, totals correct).
- R-3 Offline-authorized returns are flagged, not refused, when the manager turns out not to qualify.
- R-4 (POSR) A standalone store credit (`POST credit-notes`) has no Finance document: its later redemption books a STORE_CREDIT payment against a receivable with no matching refund — the liability exists only in the POS subledger.
- R-5 (POSR) A return whose restocking fee is 100 % posts no Finance credit note, so the product ledger gets no RETURN_IN for it (stock does come back).
- R-6 (POSR) Cross-store report recipients outside store staff come from a capped user search (100 users per org).
- R-7 (POSR) No-receipt returns/exchanges are not implemented (`requireReceipt` / `allowNoReceiptExchange` are stored and returned only) — every return starts from the original order.
