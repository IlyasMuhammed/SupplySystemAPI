# Addendum 40 — Data Import & Upload Framework: reality check & proposed tasks

Spec: SMS-FSD-ADD-040 v1.0 (C1–C9) · Register: 353 tasks · Contract: [API-CONTRACT.md](API-CONTRACT.md) · Tasks: [ADDENDUM-40-TASKS.md](ADDENDUM-40-TASKS.md) · Shared seam: `src/SMS.Shared/Common/ImportContracts.cs`.
**Status 2026-10-11: user said "start" — the 4 decisions below are ADOPTED as recommended.**

## Adopted decisions
- **D-1** Chart of accounts, GL opening balance, employees: dropped (no GL / HR).
- **D-2** Entity codes (`ImportEntityTypes`): UNIT, PRODUCT_CATEGORY, PRODUCT, WAREHOUSE, WAREHOUSE_LOCATION, TAX_CODE, CUSTOMER, SUPPLIER, SUPPLIER_CONTACT, PRICING_RULE, OPENING_STOCK, CUSTOMER_OPENING_BALANCE, SUPPLIER_OPENING_BALANCE (wizard order).
- **D-3** `IImportTarget` per entity in its owning module (Describe / GetTemplateLists / Validate / Apply-in-one-transaction). Profiles + fields are code-defined by the targets and reconciled into `import.profiles` at startup (like the A37 catalog); an org may override only duplicate strategy / limits (custom profile row).
- **D-4** Imported suppliers are created APPROVED (active vendors), recorded in the partner status history as "Imported".
- **D-5** Customer / supplier opening balances become real open documents: an issued sales invoice (SourceType OPENING, no stock, no COGS) and a supplier invoice/bill (SourceType OPENING, no PO/GRN), both in aging and payable/receivable as normal; customer/supplier ledgers get OPENING_BAL entries.
- **D-6** Price list items → `PricingRule` rows (variant SKU, optional customer code, price type, min qty, price, currency, valid from/to).
- **D-7** Opening balance date: one per org, owned by Finance (`api/finance/opening-balance-date`), read via `IOpeningBalanceDateProvider`; opening imports refused until it is set. Opening stock: stock IN at the date (inventory ledger OPENING_STOCK + master product ledger) + Finance product ledger IN at unit cost (so later sales cost correctly). One opening per variant+warehouse (IMP-OB-03 → duplicate = error).
- **D-8** Products: one default variant per row (sku/barcode/prices on it); categories: `parent_code` → the row is a sub-category of that category (2 levels); units: Lookups `uom` values (code + name); warehouse locations: zone_code (+ bin_code) per warehouse_code.
- **D-9** Permissions `IMPORT_PROFILE_VIEW IMPORT_PROFILE_MANAGE IMPORT_UPLOAD IMPORT_EXECUTE IMPORT_MANAGE IMPORT_OPENING_BALANCE`; grants: all built-in roles with any write permission get VIEW+UPLOAD; Finance Officer/Manager, Inventory Manager, Procurement Manager + EXECUTE; Finance Manager + OPENING_BALANCE; Org/System Admin all. Module `MODULE_DATA_IMPORT` (always on), sub-feature `FEATURE_OPENING_BALANCE_IMPORT` (Standard/Enterprise).
- **D-10** Files are parsed in memory (never saved under wwwroot); rows stored as JSON in `import.rows`; session rows older than 90 days purged by a daily job.
- **D-11 (TSUP)** Partner matching (CUSTOMER/SUPPLIER, MatchFields `code`,`email`): a row with a code matches the organization's partner with that code (any role — the unique index is per org across the whole BusinessPartners table); a vendor matched by a CUSTOMER row gains the customer role (and vice versa → PartnerType BOTH); a combination with no FSD PartnerType → `PARTNER_ROLE_CONFLICT`; a deleted partner's code → `CODE_IN_USE`. Email is used only when the code is blank (customers; supplier code is mandatory, max 10 chars), exactly one active customer with that email; several → `AMBIGUOUS_MATCH`. A row's `ExistingEntityUuid` (external reference) wins over the natural key. Codes are never changed on UPDATE. Email uniqueness is not enforced (it is not in the system either). A CREATE whose code already exists fails the batch (`CODE_IN_USE`) — CREATE_NEW cannot duplicate a code.
- **D-12 (TSUP)** CUSTOMER follows the A37 customer API: blank code → next `C-nnnnn` (one past the highest ever used, deleted rows and the file's explicit C-codes included); `customer_type` (extra optional column) default COMPANY; walk-in (C-WALKIN / IsSystem) is never matched or created → `WALK_IN_PROTECTED`; WALK_IN-type rows with credit > 0 → `CREDIT_NOT_ALLOWED`; `credit_limit` is written only while FEATURE_CREDIT_MANAGEMENT is on, otherwise silently ignored (no error, no warning — the contract has no warning channel), as the customer API does. `mobile` added as an optional column.
- **D-13 (TSUP)** SUPPLIER "APPROVED" (D-4) = this system's approved state: Status `ACTIVE` with ApprovedBy / OnboardingDate / StatusChangedBy/At = importer (is_active false → `INACTIVE`). There is no partner status-history table, so the history entry is an audit-log row (`SUPPLIERS / STATUS_CHANGE / SUPPLIER`, newValue status, notes `Imported`) + the normal `supplier.approved` event; no schema change. On UPDATE, is_active only moves ACTIVE⇄INACTIVE; other states (PENDING, SUSPENDED, BLACKLISTED, REJECTED) → `STATUS_CHANGE_NOT_ALLOWED`.
- **D-14 (TSUP)** `payment_terms_days` → `BusinessPartners.PaymentTermsDays` (the A37 int column, present on every partner); the Lookups payment-term id (PreferredPaymentTerms) is left untouched (no shared lookup by days). `currency_code` → default purchase currency (PreferredCurrency), must be an ACTIVE currency of the organization (IOrgCurrencyLookup) else `LOOKUP_NOT_FOUND`.
- **D-15 (TSUP)** `country_code` accepts ISO alpha-2, alpha-3 or the English name (runtime RegionInfo data) and is stored as alpha-2 (the phone validator reads Country as a region code); unknown → `LOOKUP_NOT_FOUND`. Template lists: `countries` (alpha-2), `customer_types`, `currencies` (active org codes), `suppliers` (active vendor codes, ≤1000).
- **D-16 (TSUP)** SUPPLIER_CONTACT: supplier must already be a vendor of the org (import suppliers first) else `LOOKUP_NOT_FOUND`; match supplier + email (active contacts). SupplierContacts has an int key and no UUID/audit columns, so the entity reference is a stable synthetic Guid encoding the contact id (`SupplierContactImportTarget.ToUuid/TryFromUuid`) and userId is not stored; `is_primary` true demotes the supplier's other contacts.
- **D-17 (TSUP)** Apply = one `SaveChanges` per batch (EF wraps it in one transaction; works with the retry strategy and the in-memory tests); rows are re-checked first and the first bad row throws `BadRequestException("Row n: … (CODE, field f).")`; the change tracker is cleared on failure. After commit, best-effort: QuickBooks partner publish (as normal saves), approval audit/event. All queries ignore the tenant filter and filter on the explicit organization.
- **D-18 (TINV)** Inventory/Lookups targets (`src/SMS.Modules.Inventory/Import/*`, `src/SMS.Modules.Lookups/Import/UnitImportTarget.cs`): explicit organization everywhere (IgnoreQueryFilters + org; new rows stamped with it). Codes compare case-insensitively; zone/bin/unit codes are stored upper-case (as the structure screens do). Rows with only an int key (category, sub-category, zone, bin) are referenced by a deterministic surrogate UUID (`ImportSurrogateIds`: id + hash of the kind) — no schema change, **no migrations**. Apply = ONE transaction (`ImportUnitOfWork`: own transaction under the execution strategy, or the caller's; none in-memory), rows re-checked first; any bad row → `UnprocessableEntityException("Row n: …")`; CREATE on an existing unique key (SKU, code) throws, so CREATE_NEW cannot duplicate it; change tracker cleared on failure. Targets also report DUPLICATE_IN_FILE inside the rows they are given (needed where a match key is partly empty, e.g. a category without parent).
- **D-19 (TINV)** UNIT: a Lookups `uom` value named `"{name} ({code})"` — the code is the trailing parenthesis, the seeded catalog's convention ("Piece (PCS)") and what Product.UomCode holds. Imported units are the org's own (IsGlobal false). Match among the global catalog + the org's units (own wins). An UPDATE of a global unit is never applied: outcome `SKIPPED`. Template list `units` = codes. PRODUCT reads the units through the UNIT target's template list resolved from DI (no Inventory→Lookups reference); a host without the UNIT target accepts any unit code.
- **D-20 (TINV)** PRODUCT_CATEGORY (MatchFields code, parent_code): the parent is an existing category or an EARLIER row of the file (a later one → MISSING_DEPENDENCY "put it before"; a parent row with errors → MISSING_DEPENDENCY); a parent that is a sub-category (existing or a child row) → MISSING_DEPENDENCY "only two levels"; unknown parent → MISSING_DEPENDENCY. Names unique (category per org, sub-category per parent among active) → `DUPLICATE_NAME`. An UPDATE never moves a sub-category to another parent.
- **D-21 (TINV)** PRODUCT: the row's sku is both the product SKU (max 30) and its default variant's SKU (not "-DEFAULT"). Match: product SKU, else a default variant's SKU (UI-created products match either way); a non-default variant's SKU → `SKU_IN_USE`. `category_code` = a category code or a unique sub-category code (→ that sub-category + its parent; several → `AMBIGUOUS_CODE`). Active product names unique (`DUPLICATE_NAME`, as the product API), barcode unique per org (`DUPLICATE_IN_DB`). Classification (coordinator follow-up 2), same rules as the product screens: optional `product_type` (ProductType codes, template list `product_types`) and `supply_method` (SupplyMethod codes, list `supply_methods`); unknown code → `LOOKUP_NOT_FOUND`. product_type wins over is_service; is_service saying the opposite (Yes with a non-SERVICE type, or No with SERVICE) → `RULE_VIOLATION`. product_type blank: new row = SERVICE when is_service Yes, else STOCK_ITEM; update = unchanged, except is_service Yes turns the product into a SERVICE and is_service No on a SERVICE → `TYPE_CHANGE_REFUSED` (give the new product_type). Like the edit screen's type change, a new/changed type re-defaults the supply method (unless supply_method is given) and the saleable/purchasable/stockable flags to the §6.1 row; an unchanged type keeps them. The result must pass `ProductClassificationRules.Problem` (e.g. FINISHED_GOOD needs MANUFACTURE, only semi/finished goods manufacture, a service is not stockable) → `RULE_VIOLATION`. IsManufacturable = MANUFACTURE. A type change to a type that cannot be a BOM input is refused while a variant stays available for production (ApplyClassificationAsync; the row's own `available_for_production` = No on the default variant counts), and leaving SERVICE clears the service configuration. cost_price empty → 0 on create. is_active false → Status INACTIVE (variant stays active, like the soft delete). Channel availability (coordinator follow-up): optional BOOLEAN columns `available_for_retail` (template sample "Yes"), `available_for_pos`, `available_for_mir_miv`, `available_for_production`, `available_for_services` (samples "No") → the default variant's IsAvailableFor* flags. Blank: unticked on CREATE (the variant-availability default), unchanged on UPDATE. Only the product screens' rule applies: `available_for_production` = Yes needs a type that can be a BOM input (`ProductionInputProblem` on the resolved type): STOCK_ITEM and ASSET are refused (`RULE_VIOLATION`), SERVICE is allowed (service BOMs, A36). There is no MIR/MIV rule; the earlier import-only refusal for services was dropped so import matches the screens exactly. A non-boolean → `INVALID_TYPE`. After commit, best-effort: search-index rebuild enqueued per variant, QuickBooks product publish.
- **D-22 (TINV)** WAREHOUSE: `country_code` stored as given in Warehouse.Country (free text there, no country lookup). WAREHOUSE_LOCATION: warehouse must exist (`LOOKUP_NOT_FOUND`); a bin row creates its zone when missing (name = zone_name ?? zone code); bin_name → Bin.Description (a bin has no name); zone_name on any row renames the zone; match warehouse + zone (+ bin).
- **D-23 (TINV)** PRICING_RULE: sku = variant SKU, or product SKU (→ default variant); the product must be saleable. Price types SELLING / PROMOTIONAL / CONTRACT (COST not importable); CONTRACT needs a customer (as PricingRuleService). customer_code is resolved through the Shared `IPosCustomerSource` (Suppliers' customer source, explicit org, paged until found) — `IImportPartnerLookup` lives in Finance, not Shared; inactive customer refused. currency_code via `IOrgCurrencyLookup` (active org currency), empty → the sale base currency (`IOrganizationCurrencyService`). valid_from empty → today. Match = active rule of the same variant + customer + type + min qty starting on valid_from (no valid_from: the latest such rule); UPDATE changes price, currency (when sent), valid_to; CREATE_NEW simply adds another rule (rules are not unique).
- **D-24 (TINV)** OPENING_STOCK (IsOpeningBalance, AllowUpdate false): no provider or no date → every row `OPENING_DATE_NOT_SET` (field "") with the contract message. One opening per variant + warehouse, and per batch for a batch-tracked product (ledger ReferenceNumber `OPENING` / `OPENING/{batch}`, batch ≤ 42 chars): an existing OPENING_STOCK ledger entry → `DUPLICATE_IN_DB`; Apply refuses UPDATE rows. Serial-tracked → `SERIAL_TRACKED`; not stockable → `NOT_STOCKABLE`; batch on a non-batch product → `BATCH_NOT_TRACKED`; `location_code` = BIN or ZONE/BIN of that warehouse. Posting per row, in Inventory's one transaction: InventoryItem IN (bin, batch, expiry; an existing default row gets the qty added at weighted cost), inventory ledger `OPENING_STOCK` / ref type `OPENING_STOCK` dated at the opening date (new optional `LedgerEntryCommand.TransactionDate`), master product ledger OPENING_BALANCE → WAREHOUSE (also dated at the opening date via TFIN's new `ProductMovementContext.TransactionDate`, passed through by InventoryLedgerService), Finance product ledger IN at unit cost with EntryDate = opening date, enlisted in the transaction like EfGrnInventoryPoster. Product ledger entry type = `ADJUSTMENT` (ProductLedgerEntryTypes has no OPENING; the target picks OPENING / OPENING_STOCK / OPENING_BALANCE automatically if Finance adds one). Quantity 0 → the opening is recorded (ledger row) but no product ledger entry. Outcome uuid = the ledger ReferenceId.

- **D-30 (IMP)** Role grants by role CODE (`AuthDataSeeder.ImportGrants`, only missing grants added): VIEW+UPLOAD to Procurement Manager, Purchase Officer, Inventory Manager, Warehouse Operator, Finance Officer, Requester, Finance Manager, Supply Dept Admin; + EXECUTE to Procurement Manager, Inventory Manager, Finance Officer, Finance Manager; + OPENING_BALANCE to Finance Manager; System/Org Admin all (via `PermissionCodes.All`). Auditor (read-only) and the POS till roles get none — a cashier is not a data-entry role. Role-editor group "Data Import"; `IMPORT_` → MODULE_DATA_IMPORT in ModuleCodeMap.
- **D-31 (IMP)** `MODULE_DATA_IMPORT` is core + always on in every plan. `FEATURE_OPENING_BALANCE_IMPORT` is excluded from Basic; an existing organization gets it from its PLAN (`TenancyFeatureCatalog.PlanDefaultForExistingOrgs`), because the A37 "sub-feature follows its module" backfill rule would switch it on for Basic orgs (the module is always on).
- **D-32 (IMP)** Runtime profiles/fields come from the registered targets' `Describe()`; `import.profiles`/`profile_fields` are a startup mirror (inactive when a target disappears). Every profile gets the importer's own `external_id` field first (TEXT 100, aliases ext_id/legacy_id/source_id); targets never see `external_id` in their values. Defaults: strategy SKIP (opening balances forced ERROR), 50 000 rows, 10 MB; an org override may only lower the limits.
- **D-33 (IMP)** Validation hands ALL generically valid rows to the target in ONE `ValidateAsync` call (files ≤ 50 000 rows) so in-file hierarchy anywhere earlier in the file is visible. An existing record resolved through the external reference wins over the target's natural-key match. The importer raises DUPLICATE_IN_DB when a match exists and the strategy is ERROR, UPDATE on a no-update profile, or CREATE_NEW ("CREATE_NEW cannot create a duplicate of an existing {match fields}").
- **D-34 (IMP)** Execution: a batch whose `ApplyAsync` throws (any exception, e.g. BadRequest/UnprocessableEntity) is marked ERROR / IMPORT_ERROR; when the message starts "Row n:" that row carries the message and the others "Batch rolled back because of row n."; the import continues. Outcome status SKIPPED counts as skipped (no external reference registered). Final status: no invalid/error rows → COMPLETED; nothing applied → FAILED; else COMPLETED_WITH_ERRORS. Cancel stops before the next batch; applied batches stay. A filtered unique index keeps one IMPORTING session per org + entity type. Background job sets `HangfireTenantScope` to the session's org.
- **D-35 (IMP)** Templates: help (row 2) and sample (row 3) rows are skipped on upload only while they still hold exactly the generated content (row hashes in workbook custom properties); overwritten rows are data. Error report = failed rows only (re-uploadable, original headers) + summary by code; results report = every row with status and record uuid.
- **D-36 (IMP)** Field type CURRENCY = a 3-letter currency CODE (trimmed, upper-cased; else INVALID_TYPE); money amounts are DECIMAL.
- **D-37 (IMP)** Session visibility: IMPORT_UPLOAD sees only its own sessions, IMPORT_MANAGE all of the org's; another user's session reads as 404.
- **D-38 (IMP)** Interrupted imports: `ImportRecoveryJob` (startup + every 10 min) turns an IMPORTING session whose last batch save (`ModifiedAt`) is older than 30 min and that has no live Hangfire job (enqueued / scheduled / awaiting / processing; job storage unreachable → left alone) into FAILED with "Import interrupted — re-validate and re-run the remaining rows." — freeing the one-IMPORTING index. Cancel of an IMPORTING session by an IMPORT_MANAGE holder forces the same FAILED/interrupted state (others still get CANCELLED). A running loop stops before its next batch whenever the session is no longer IMPORTING.
- **D-39 (IMP)** Safe re-runs: each batch's row outcomes, external references and counters are committed before the next batch starts. A FAILED or CANCELLED session can be validated again (execute then requires VALIDATED): only rows still PENDING/VALID/INVALID are re-checked — IMPORTED/UPDATED/SKIPPED/ERROR rows keep their outcome and counters accumulate. A row the target committed but the importer never marked is still VALID; on re-validation the target's natural-key match returns its ExistingEntityUuid, so it becomes SKIPPED (SKIP), UPDATED (UPDATE) or DUPLICATE_IN_DB (ERROR, CREATE_NEW, opening balances) — never a second record. Tested for all four strategies + opening stock.
- **D-47 (IMP, FE follow-up)** `PUT mappings` saves an incomplete mapping and refuses only double mapping (IMP-MAP-03), unknown fields/columns and started imports; IMP-MAP-01/02 (required / key fields) are enforced by `validate` (execute needs VALIDATED, so it is covered). IMP-FILE-08 counts only IMPORTING sessions — the UPLOADED session left when the user picks another sheet never blocks; the recovery job sets an UPLOADED session untouched for 7 days to CANCELLED ("Cancelled automatically: not mapped or validated within 7 days."). `ImportProfile.lastCompletedSessionUuid` added (newest COMPLETED / COMPLETED_WITH_ERRORS).
- **D-40 (TFIN)** Opening balance date: new table `finance.org_settings` (one row per org, `OpeningBalanceDate date NULL`; migration `A40_FinanceOrgSettings`, guarded/idempotent). `GET api/finance/opening-balance-date` → `{ date }` (any of FINANCE_SETUP_MANAGE, INVOICE_VIEW, PAYMENT_VIEW, SALES_INVOICE_VIEW, CUSTOMER_LEDGER_VIEW, IMPORT_OPENING_BALANCE, and — FE follow-up, for Settings › Finance Setup › Currency configuration — CURRENCY_VIEW, CURRENCY_MANAGE, CURRENCY_RATE_VIEW, CURRENCY_RATE_MANAGE, ORG_CURRENCY_SETTINGS_MANAGE); `PUT { date: 'yyyy-MM-dd' | null }` (FINANCE_SETUP_MANAGE + MODULE_FINANCE). Not before 2000-01-01; refused (409) to clear it once opening documents exist, or to move it before the latest imported opening document date. `OpeningBalanceDateService` implements `IOpeningBalanceDateProvider` (explicit org).
- **D-41 (TFIN)** Finance targets: explicit organization (must equal the caller's tenant unless super admin; rows stamped explicitly), Apply re-checks the batch, first bad row → `BadRequestException("Row n: …")`, one `SaveChanges` per batch (TAX_CODE: own transaction under the tax-code screen's per-org app lock), change tracker cleared on failure. Partners by code come from a new seam `SMS.Modules.Finance.Import.IImportPartnerLookup`, implemented in Suppliers (`ImportPartnerLookup`, registered in `ISuppliersModule`) — the A38 `ICustomerPaymentTermsLookup` pattern; no Shared code-lookup existed. Extra error codes: OPENING_DATE_NOT_SET, AFTER_OPENING_DATE, NOT_A_CUSTOMER, NOT_A_SUPPLIER, INACTIVE_PARTNER, NO_EXCHANGE_RATE, MULTIPLE_DEFAULTS.
- **D-42 (TFIN)** TAX_CODE: fields code, name, rate_percent, usage (blank = BOTH on create), is_default, description, is_active; match code (case-insensitive, stored upper-case); TaxCodeService rules (pattern, 0–100 / 2dp, one default per side — an imported default dethrones the existing ones; two rows of one file defaulting the same side → MULTIPLE_DEFAULTS; an inactive code is never default). UPDATE leaves blank fields unchanged. Template list `tax_usages`.
- **D-43 (TFIN)** CUSTOMER_OPENING_BALANCE → an ISSUED `SalesInvoice` SourceType `OPENING` (SourceNumber = invoice_reference, SourceUuid = name-based uuid of org+customer+upper(ref) so the existing unique (org, SourceUuid) index refuses a second one, blank ref = one per customer), one line "Opening balance {ref}" with `VariantUuid = Guid.Empty` (no product ledger, no COGS), number SINV-{invoice date}-NNNN, due = due_date or invoice date + customer terms (30 when none), rate locked at the invoice date against the sale base (blank currency = sale base; currency must be an active org currency, a foreign one needs a rate on that date). Customer ledger entry **OPENING_BAL** (ReferenceType SalesInvoice, dated the invoice date) — so the sales reports (INVOICE entries) leave it out; Reports' R3 aging now counts OPENING_BAL entries too (one-line change in `ReceivablesReportService`). Pays, ages, goes OVERDUE, cancels and shows in ICustomerBalanceLookup like any invoice.
- **D-44 (TFIN)** SUPPLIER_OPENING_BALANCE → an **Approved** supplier `Invoice` SourceType `OPENING` (no PO/GRN, the G10 shape), SupplierInvoiceNo = bill_reference, SourceUuid name-based (unique (SourceType, SourceUuid) index), one line, INV-yyyy-NNNNN, due = due_date or bill date + 30, rate locked at the bill date against the purchase base, ApprovedBy/CreatedBy = importer. Ledgers as an approval writes them: supplier ledger + master financial ledger **INVOICE_APPROVED** debits dated the bill date (not OPENING_BALANCE: a reversal looks for INVOICE_APPROVED, and the A24 one-time OPENING_BALANCE import guard must not trip). Paid by supplier payments, reversible. FE follow-up: supplier invoice `InvoiceListItemModel` / `InvoiceDetailModel` expose `sourceType` (OPENING, CARRIER_INVOICE or null) for the "Opening balance" chip.

Payments are not synced anyway (QBI D-8). Flip = remove the two predicates.
- **D-46 (TFIN, for TINV)** `ProductLedgerEntryTypes.OpeningStock = "OPENING_STOCK"` (IN only, needs a unit cost, averaged into WAC like a purchase; the product-ledger summary counts it with purchases; the entry-type filter accepts it). `ProductMovementContext.TransactionDate` (optional, default now) dates the master product ledger row. No migration (EntryType nvarchar(20), no check constraint). TINV's target picks the type up by name; InventoryLedgerService already passes the date.

## Part B — proposed tasks (what would be built)

1. **Import module foundation (Import)** — schema `import`: profiles + fields (seeded in code for the 12 kept entity types, reconciled at startup like the A37 catalog), sessions, column mappings, rows (JSON), external references; profile list/detail APIs.
2. **Upload & parsing (Import)** — `.xlsx` (ClosedXML) and `.csv` (CsvHelper) parsing, file rules IMP-FILE-01..08 (type, 10 MB, 50 000 rows, header, empty, sheet choice, immutability, one active import per entity per org).
3. **Column mapping (Import)** — 4-tier auto-mapping (exact / normalized / alias incl. SAP-style names / fuzzy Levenshtein ≥0.70), external_id aliases, rules IMP-MAP-01..04, saved presets.

## Residuals (expected)
- R-1 No journal entries for opening stock/balances (no GL); QuickBooks receives opening documents only if they are normal invoices/bills.
- R-2 Product import creates one default variant; multi-variant import is a later step.
- R-3 Units have no conversion ratios in this system.
- R-4 (IMP) The importer's row marking is a separate transaction from the target's batch commit. A crash between the two leaves that batch's rows VALID; recovery (D-38) and re-validation (D-39) make the re-run safe for every target whose match fields find the record it created (all current targets have match fields). Limits: (a) a target with no natural-key match would re-create the rows; (b) with UPDATE the batch is applied a second time (idempotent values); (c) ERROR rows (rolled-back batches) are final and are not retried by a re-run — re-import them from the error report; (d) the external reference of an applied-but-unmarked row is registered only when the re-run updates it (SKIP / DUPLICATE leave it unregistered).
