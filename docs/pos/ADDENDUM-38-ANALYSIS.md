## Part B — proposed decisions

- **D-1 Module & conventions.** New module project `SMS.Modules.Pos` (own `PosDbContext`, schema `pos`, int Id + Guid UUID, OrganizationId tenant filter, string status codes, RowVersion on Store/Terminal/Shift/Order). Talks to Inventory/Finance/Suppliers/Auth only through Shared interfaces. Migrations additive + guarded (startup migrates SMSGlobal).
- **D-2 Licensing.** `MODULE_POS` available; depends on INVENTORY, CUSTOMERS, FINANCE; **excluded from BASIC**, default in STANDARD/ENTERPRISE for *new* orgs; existing orgs get it only when the super admin licenses it. Sub-features per spec Appendix C (POS_RETURNS, POS_CREDIT_SALES, POS_BARCODE, POS_MULTI_STORE toggleable; analytics/promotions/loyalty coming soon).
- **D-3 Store/terminal.** `pos.stores` 1:1 `WarehouseUuid` (POS-STR-02 enforced, filtered unique index); currency = org sale base (single-currency POS, spec §1.2); timezone drives shift/order dates. `pos.terminals` with device binding as specified.
- **D-4 Cashier identity.** `UserAccount.PosPinHash` (existing PBKDF2 hasher), `PosRole` (CASHIER|SUPERVISOR), `PosPinFailedAttempts/LockedUntil`; store staff via `pos.store_staff` (user ↔ store, many-to-many — a user may work in several stores). PIN unique per store. **Online switch**: `POST api/pos/auth/pin` with the terminal's token returns a token pair for the cashier (same org enforced by the tenant filter), so every API call runs with the *cashier's own* permissions. **Offline**: PIN hashes of the store's staff cached on the device **(discuss — a 4–6 digit PIN hash is brute-forceable by anyone holding the device; mitigations: per-device salt, cache only for bound devices, wipe on unbind, offline sessions re-verified at sync)**.
- **D-5 Shift & cash.** As specified (DRAFT→OPEN→CLOSING→CLOSED→RECONCILED|DISPUTED, cash movements, variance threshold, stale-shift job). Totals are recomputed from orders/payments/movements, not trusted from the client.
- **D-6 POS catalog data.** Use variant Barcode / SellingPrice / IsAvailableForPos (now **enforced** for POS). New `pos.variant_pos_settings` only for POS name, POS category, colour, favourite, weighable, sort order, image override. Price = `IPricingService` resolution baked into the POS catalog sync per store (server computes, device caches).
- **D-7 Numbers.** Own `pos.number_sequences` (store, day) → `POS-{store}-{yyyyMMdd}-{seq}`, `SH-…`; offline temporary `POS-{store}-OFF-{short}` replaced at sync (spec).
- **D-8 Money (discuss).** Each completed POS order becomes **one issued `SalesInvoice`** (counter sale: no SO/delivery; SO refs nullable; source `POS`) **plus one `CustomerPayment` per tender**, allocated to it — so it appears in sales analysis, receivables, customer ledger, product ledger (COGS at WAC) and QuickBooks. Credit sale = invoice without payment (balance on the customer). Payment methods map CASH/CARD/BANK_TRANSFER/CHEQUE as today + new MOBILE. *Alternatives*: one summary invoice per shift for cash/card sales (fewer documents, less QuickBooks noise; credit sales still per order). *Known gap*: QuickBooks receives invoices but **payments are not synced** → POS sales show as unpaid A/R in QuickBooks until payment sync is added (R-2).
- **D-9 Negative stock (discuss).** Spec says sell even at zero stock. Today nothing can go below zero and Finance refuses COGS beyond its running quantity. Options: (a) **allow negative for POS only** — Inventory posting path that lets on-hand go negative + notification + daily negative-stock report, and Finance product ledger accepting a POS OUT below zero at last WAC; (b) refuse online, accept offline-synced sales with a "stock exception" queue for a supervisor. Proposed: (a), because offline sales already happened.
- **D-10 Returns, voids, refunds.** New in Finance: customer **credit note / return document** (partial, line-level, links original invoice; customer ledger CREDIT_NOTE, product ledger RETURN_IN at original cost, refund payment REFUND) and **payment reversal**. POS void = credit note for the whole order + payment reversal + stock back, same shift only. QuickBooks credit-note sync is refused today (R-3).
- **D-11 Tax.** Store default sales tax code (Finance TaxCode); per-line override from the variant's category is not available (no product tax) — line uses the store default unless the cashier picks another. Store `TaxInclusivePricing`: price back-solved to exclusive, rounding difference absorbed on the last line so the receipt total equals the shelf price.
- **D-12 Credit sales.** Online: `ICustomerBalanceLookup` + CreditLimit (CUST-03 first enforcement). Offline: cached balance × (1 + store tolerance %); over-limit discovered at sync → CREDIT_OVER_LIMIT flag + notification to the store supervisors. Walk-in (`C-WALKIN`) never on credit.
- **D-13 Permissions.** `POS_STORE_VIEW/MANAGE`, `POS_TERMINAL_VIEW/MANAGE`, `POS_SHIFT_OPEN/CLOSE/RECONCILE/VIEW`, `POS_ORDER_CREATE/VIEW/VOID/RETURN/DISCOUNT`, `POS_CASH_MOVEMENT`, `POS_PRODUCT_SETTINGS`, `POS_CUSTOMER_SETTINGS`, `POS_REPORTS_VIEW`. New built-in roles **POS_CASHIER**, **POS_SUPERVISOR**, **STORE_MANAGER** per spec §16.2; Org Admin all.
- **D-14 Sync API.** Orders pushed with client `localId` (idempotent, POS-SYN-05), batch endpoint, server recomputes totals/tax and is the source of truth; catalog/customer pull reuse `/api/sync/*` with a `storeUuid` extension (POS settings, resolved price, store stock snapshot). Stock snapshot for the store warehouse needs a stock delta source (InventoryItem has no ModifiedAt) — snapshot on full sync + SignalR `StockUpdated` pushes.
- **D-15 Real-time.** `PosHub` at `/hubs/pos`, groups `org_{org}_store_{uuid}` / `org_{org}_terminal_{uuid}`, module + permission check on connect, events per spec §12.3 raised from the existing price/stock/customer write paths.
- **D-16 Frontend.** Selling screen, payment, receipt (HTML + `window.print()`), shift screens in the SMS Flow tokens (touch-sized); back-office pages (stores, terminals, staff/PINs, shifts, POS orders, product POS tab, customer POS settings) in the portal. Camera barcode via the browser `BarcodeDetector` where available, keyboard-wedge scanners always.
- **D-17 (XMOD) PIN storage only on UserAccount.** Auth adds just `PosPinHash` (nvarchar(256) NULL, guarded migration `A38_UserPosPinHash`). D-4's `PosRole` and `PosPinFailedAttempts/LockedUntil` are **not** on UserAccount: the POS role belongs to `pos.store_staff` and PIN lockout is per terminal (API-CONTRACT §3) — both POSA. `IPosPinService` never touches `FailedLoginAttempts/LastFailedAt/LockedUntil` (the password lockout), in either direction (a password-locked user can still use their PIN; a PIN sign-in does not clear the password lock). PIN = `^[0-9]{4,6}$` (not `\d`, which accepts full-width/other-script digits); null or "" clears. Hash = the existing `PasswordHasher<UserAccount>` (Identity v3: 0x01, PRF 2 = HMAC-SHA512, 100 000 iterations, 16-byte salt, 32-byte subkey on .NET 8).
- **D-18 (XMOD) Who a PIN can identify.** `VerifyAsync`/`FindByPinAsync`/`GetPinHashesAsync` consider only active, non-deleted users of the given organization with a PIN; `FindByPinAsync` returns **null when more than one candidate matches** (never guesses between two staff). POSA must keep PINs unique per store at assignment (`"This PIN is already used by another staff member of this store."`) — `SetPinAsync` has no store context. Each verify is a full PBKDF2 (≈ tens of ms): a `userId`-less PIN sign-in over a large store's staff is proportionally slower — POS should pass the store's PIN holders only.
- **D-19 (XMOD) PIN sign-in tokens.** `IssueTokensAsync` builds the same JWT (same permission computation — `AuthRepository.ComputeAllowedPermissions`, now shared with login) and records a `UserSession` (7-day refresh, OrganizationId set from the user, not the ambient tenant) and `LastLoginAt`. Refused (UnauthorizedException): unknown/deleted/other-org user ("This user cannot sign in."), inactive user, inactive organization, and **platform super admins** ("Platform super admins cannot sign in with a PIN." — a 4–6 digit PIN must not unlock platform administration). Permission/role checks (POS_ORDER_CREATE, store staff) are POSA's.
- **D-20 (XMOD) Existing organizations stay unlicensed.** `TenancyFeatureCatalog.LicensedByHandForExistingOrgs = {MODULE_POS}`: the startup backfill creates a missing MODULE_POS row unlicensed and off whatever the org's plan (an org that already has the A37 "coming soon" row keeps it as is — unlicensed). New orgs (`CreateOrganizationWithAdminAsync`) get it from the plan template (Standard/Enterprise on, Basic off). An SCM-DEMO created by the seeder in the same start (fresh database) counts as new and gets POS; an SCM-DEMO that already existed does **not** — the super admin licenses it (Organizations → modules), as for any existing org. "Apply plan template" by the super admin also licenses it (explicit action).
- **D-21 (XMOD) POS sub-features.** Core (IsCore, licensed with the module): FEATURE_POS_ORDERS, _SHIFTS, _CASHIER_PIN, _PAYMENTS, _OFFLINE. Toggleable: FEATURE_POS_RETURNS, _CREDIT_SALES, _BARCODE, _MULTI_STORE (in the Standard/Enterprise templates, on for new orgs). Coming soon (IsAvailable=false): FEATURE_POS_ANALYTICS, _PROMOTIONS, _LOYALTY. Per the A37 backfill rule, an existing org's core POS sub-feature rows are created licensed+on but count as enabled only while MODULE_POS is (snapshot); toggleable ones follow the module's (unlicensed) state.
- **D-22 (XMOD) Roles.** POS_CASHIER / POS_SUPERVISOR / STORE_MANAGER are global built-in roles matched by RoleCode; RoleSeed labels 12/13/14 (no EnumRole values added — SMS.Shared Enums untouched). A new built-in role (seed id ≥ 12) never takes an id that still carries orphaned RolePermissions or UserAccounts (no FKs; the live DB has had roles deleted by hand) — it goes to max(taken)+1; the pre-A38 roles keep the old rule. STORE_MANAGER also gets CUSTOMER_VIEW (§9). Every role also receives CURRENCY_VIEW/CURRENCY_RATE_VIEW (A35 D-16). Org Admin / System Admin hold all 17 via `PermissionCodes.All`.
- **D-23 (XMOD) Customer source.** `PosCustomerSource` follows the A37 customer sync: IsCustomer partners of the explicit org (tenant filter ignored), `ModifiedAt` strictly after `since`, oldest first, deactivated/deleted included with `IsActive=false`, a page extended to the end of a run of equal ModifiedAt (may exceed `limit`), limit clamped to 1..1000. `GetAsync`/`GetManyAsync` return inactive customers (POS explains the refusal) but not deleted ones, vendors or other orgs'. `GetWalkInAsync` ensures it via the A37 `WalkInCustomerSeeder`; the system row wins, else a partner already coded C-WALKIN. CustomerType null ⇒ COMPANY, CreditLimit null ⇒ 0 (as CustomerService).
- **D-24 (INV) POS stock postings (`PosStockPoster`).** Explicit org (tenant filter ignored; unknown/other-org warehouse or variant ⇒ BadRequest). Validated: type ∈ POS_SALE/POS_RETURN/POS_VOID with matching direction, qty > 0; duplicate variant lines summed. **Sale**: no reservation; free stock per row (OnHand − Reserved > 0) taken FEFO (expiry, then oldest row), batch/serial rows included; the shortfall goes onto the variant's default row (no batch/serial — the one the filtered unique index allows; created with BinId null when missing), which may go negative. Other documents' holds are never consumed and QtyReserved is never changed — on an untracked variant (single row) that means OnHand can drop below QtyReserved. **Return/void**: added to the default row (not the batches the sale took: the ledger records no inventory-row id; re-shelved units go untracked). Cost: the touched row's UnitCost; new/default rows get the store's on-hand-weighted average, else last known row cost, else variant LastPurchasePrice ?? PurchasePrice. Ledger: one row per inventory row touched (saved per entry so BalanceAfter chains), ReferenceType POS_ORDER (sale/void) / POS_RETURN, ReferenceId = SourceUuid, ReferenceNumber = SourceNumber; Source/Destination WAREHOUSE→CUSTOMER (sale) / CUSTOMER→WAREHOUSE (in), so the master product ledger mirrors it in the same transaction. **Idempotent** on a ledger row with (ReferenceId, TransactionType) — new index, migration `A38_PosLedgerReferenceIndex` (guarded); a repeat posts nothing and returns the current negatives. **NegativeVariantUuids** = touched variants whose warehouse *available* (Σ OnHand − Reserved) is < 0 after the posting — stricter than the contract's "on-hand" wording, because overselling reserved stock is the same problem for the supervisor. Non-stockable products (services) move no stock. Own transaction under the execution strategy (joins a caller's), retried ×3 on DbUpdateException (RowVersion race, two first sales creating the same default row). `GetLevelsAsync` = Σ(OnHand − Reserved) per variant in the warehouse, may be negative; variants with no row are absent (= 0).
- **D-25 (INV) POS change hooks, once, in `InventoryDbContext.SaveChanges`.** Collected before the save, sent after it (`Data/PosChangeHooks.cs`): InventoryItem added/deleted or QtyOnHand/QtyReserved modified ⇒ `OnStockChangedAsync` grouped per (org, warehouse); variant SellingPrice change ⇒ `OnPriceChangedAsync(old, new)`; any other variant edit, a new/deleted variant, or a product edit (fanned out to all its variants) ⇒ `OnVariantsChangedAsync` (a price-only edit does not also raise it). Delivery: outside a transaction right after the save; inside a transaction this context began ⇒ on commit (interceptor), dropped on rollback; inside a transaction enlisted from another context (`UseTransaction` — MIV, production/service issues) the commit is invisible ⇒ dispatched in the background so the listener's reads wait for it (may fire for a later rollback — harmless, terminals re-read). Always in a **fresh DI scope** (listener never shares this context/connection); every failure logged and swallowed; skipped when no `IPosChangeListener` is registered. The context gained an optional `IServiceProvider` constructor parameter (2-arg constructor unchanged for tests/design time).
- **D-26 (INV) POS catalog source (`PosCatalogSource`).** Every variant of the org (inactive, non-saleable, non-POS included) so the PWA can drop them; `IsActive` = variant && product active; `VariantName` null for a product's default variant; `ModifiedAt` = later of variant and product (UTC); `GetChangedAsync` strictly after `since`, oldest first, limit clamped 1..1000, a full page extended with the rest of a run of equal ModifiedAt (like D-23). Price = SellingPrice ?? 0 — any `IPricingService` resolution per store (D-6) is POS-B's. Categories = active ones, by name. IsSaleable / IsAvailableForPos are exposed, enforced only by POS.
- **D-27 (INV) Labels.** POS_SALE / POS_RETURN / POS_VOID added to the transaction-type filters of the master product ledger page (+ CUSTOMER party type) and the stock reports ledger tab. No backend list enumerates ledger types.
- **D-28 (POSA) Terminal concurrency stamp.** `pos.terminals.RowVersion` is an app-rotated `binary(8)` concurrency token, rotated only by back-office edits (PUT, bind, unbind, deactivation with the store) — not SQL rowversion — so heartbeats, sync stamps and PIN failures never make an open edit form stale. Stores, shifts and orders keep SQL `rowversion`. Hub heartbeats write `lastSeenAt` at most every 60 s.
- **D-29 (POSA) PIN rules.** The PIN is per user (one `PosPinHash`), so uniqueness is checked against the active staff of **every** store the user works in (only colleagues that have a PIN are hashed). Sign-in without `userId` tries only the store's active staff who have a PIN. Only a wrong PIN counts toward the lockout; malformed PIN / not staff / no POS_ORDER_CREATE / inactive user answer 400 without counting. The 5th failure resets the counter and locks 5 min; the lock time is shown in store-local time. PIN pattern `^[0-9]{4,6}$` as in D-17.
- **D-30 (POSA) Stores.** Warehouse 1:1 among **active** stores (filtered unique index `IsActive = 1`; a deactivated store releases its warehouse; re-activation re-checks); the warehouse cannot change once the store has shifts. No default tax code given ⇒ Finance's default sales code; code + rate are snapshotted on save and the DTO shows the live Finance values when readable. `currencyCode` is resolved live (org sale base, A35), not stored. Timezone validated (IANA or Windows id), default `UTC`. `isActive` in PUT runs the PATCH status rules. FEATURE_POS_MULTI_STORE off ⇒ creating/activating a second active store is refused.
- **D-31 (POSA) Shifts.** Close is allowed from OPEN or CLOSING; `actualCashClosing` required; |variance| ≤ threshold ⇒ RECONCILED with `reconciledBy` = closer, else DISPUTED (variance note optional). Close ends the shift's active sessions. Reconcile/supervisor notes are appended to a new `reconcileNotes` field (RECONCILED and DISPUTED). Totals exclude VOIDED sales; refunds = refund payments (ON_ACCOUNT refunds count as "other"). Late orders recompute a closed shift's totals and variance without changing its status. "Own terminal" read access = POS_ORDER_CREATE + active staff of the shift's store; opening a shift and cash movements need active store staff (or POS_STORE_MANAGE).
- **D-32 (POSA) Hub groups & admin pushes.** Besides the store/terminal groups every connection joins `org_{org}_pos` on connect (MODULE_POS + any POS_* permission claim required, else aborted); org-wide catalog/customer events go there, stock/config to the store group. Unbind pushes `ForceLogout { reason: "UNBOUND" }`; force-logout also ends the terminal's active cashier session; store/terminal/staff edits push `ConfigChanged { configType: STORE|TERMINAL|STAFF }`.
- **D-33 (POSA) Staff removal** is soft (`isActive=false`, row kept) and ends that user's active sessions in the store; PUT re-activates.
- **D-34 (POSA) Stale shifts.** Hourly at :05; a shift OPEN/CLOSING for ≥ the store's `autoCloseShiftHours` (default 12) is reported **once** (`StaleAlertedAt`) — notification type `POS_STALE_SHIFT` to the store's active SUPERVISOR staff + `ShiftAlert` (WARNING) to the terminal. Nothing is auto-closed (the drawer must be counted).
- **D-35 (FIN) Counter-sale invoice.** `ICounterSaleService` = `CounterSaleService` (Finance DI). A POS sale is a `finance.sales_invoices` row with `SourceType='POS'`, `SourceUuid` = POS order (filtered unique `(OrganizationId, SourceUuid)` = idempotency for sale, return and void alike), `SourceNumber`, `SaleOrderUuid`/`SoLineUuid` NULL, `SaleOrderNumber` ''. Lines stored as given (UnitPrice, `DiscountAmount`, `TaxAmount`, TaxPercent/code, LineTotal; DiscountPercent 0); header `Tax = ΣTaxAmount`, `Discount = ΣDiscountAmount`, `Grand = ΣLineTotal`, `Subtotal = Grand − Tax + Discount` (so Subtotal − Discount = Σ net = report revenue). Currency = org sale base, rate locked through `ICurrencyService` (1). Issued through `SalesInvoiceService.TrackIssueBookingsAsync` — the same code `IssueAsync` now uses (INVOICE debit, SALE per line) — with the ledger entries dated at the sale time (offline sales keep their day); one `CustomerPayment` per non-ON_ACCOUNT tender (`SourceUuid` = tender, MOBILE method added, cheque number = reference or POS number) allocated with the back office's own `Apply`; all one `SaveChanges`; QuickBooks publish after commit (private note `POS {number}`). Due date = sale day when fully paid, else + `BusinessPartner.PaymentTermsDays` (via `ICustomerPaymentTermsLookup`, implemented in Suppliers) or 30 when 0/unknown. Invariants refused with 400: LineTotal = Net + Tax, 2dp money / 4dp qty, unique line + tender ids, Σ tenders = Σ LineTotal exactly, total > 0. Every row is stamped with the request's organization; a non-super-admin caller of another organization is refused. A back-office **cancel of a POS invoice is refused** (void/return at the POS).
- **D-36 (FIN) Negative COGS and the WAC rule.** Only POS sale OUTs may exceed the product ledger's running quantity (`IProductLedgerWriter.TrackEntryAsync(posting, allowNegative)`); everything else is refused as before (a back-office invoice for a variant driven negative stays refused). Shortfall costing (`WeightedAverageCosting.OutAllowingNegative`): units held leave with all their value; the short units at the current WAC (value/qty while qty > 0, else the variant's last entry's unit cost, 0 with no history); running qty and value go negative (−short × cost). **A later IN onto a negative quantity is the ordinary IN** (`value += qty × receipt cost`, IN TotalCost stays qty × cost): value is conserved — the provisional-vs-actual difference of the short units stays in the running value and leaves through the next sales' WAC. Known edge: a receipt far cheaper than the provisional cost can leave a positive qty with a negative value (negative WAC) until it sells through.
- **D-37 (FIN) Customer credit note = a `sales_invoices` row with Status `CREDIT_NOTE`** (the status already existed, "a negative invoice", and is already excluded from payment planning, invoiced quantities, aging candidates and the balance lookup) — smaller than a new table: same numbering, lines, PDF/list, QuickBooks source. Number `SCN-yyyyMMdd-NNNN`; amounts positive; `OriginalInvoiceUuid` + per-line `OriginalLineUuid`; `BalanceDue` 0; `CreditedAmount` = the part applied to the original invoice. Return lines: amounts as given, capped per original line by quantity ("Return quantity cannot exceed the original quantity.") and by LineTotal; Σ refunds = return total. Ledger CREDIT_NOTE credit (ReferenceType `SalesCreditNote`), RETURN_IN per line at the original sale's average unit cost (its SALE entries; none booked ⇒ none taken back). Refunds: non-ON_ACCOUNT → `finance.customer_refunds` row (`CRF-…`, method, reference, tender uuid) + ledger **REFUND debit**; ON_ACCOUNT → applied to the original invoice's balance up to what it owes (any excess stays as credit on the customer's ledger, not on an invoice). Original invoice: `ReturnedAmount += total`, `CreditedAmount += applied`, `BalanceDue = Grand − Paid − Credited`; status PAID when nothing is owed (a fully returned or voided sale reads PAID with ReturnedAmount = GrandTotal — no new status), else OVERDUE past due, else PARTIALLY_PAID / ISSUED.
- **D-38 (FIN) Void.** `VoidSaleAsync`: refused if the sale has any credit note / return or a back-office (non-POS) payment applied; each POS payment is reversed (`CustomerPaymentService.TrackReversalAsync`: REVERSED, allocations **deleted**, invoice paid amount back, PAYMENT debit, exchange differences reversed) and a full credit note (all lines, applied in full) is booked — ledger nets to zero, stock back at the sale's cost. Result `RefundUuids` is empty for a void (the money is the reversed payments, visible as REVERSED). Same-shift rule is POS's.
- **D-39 (FIN) Reports / receivables.** Balance lookup (Suppliers) unchanged: it reads open invoices' `BalanceDue`, which a return/void now reduces; credit notes and settled invoices are not open. Aging (R3) subtracts the credit notes dated by the as-of day (`CreditedAmount`) — the only Reports receivables change; customer statement (R2) is ledger-driven (CREDIT_NOTE/REFUND show as entries). Sales analysis: R4 revenue of a POS line = LineTotal − TaxAmount, R5 counts a POS sale as its own order, R4/R5/R8 subtract credit notes booked in the range (R8 also their RETURN_IN cost). Product profitability (Finance `ProductLedgerQueryService`, also what R10 wraps) reads POS line revenue the same way and nets credit notes: RETURN_IN entries referenced `SalesCreditNote` in the period come off COGS and quantity, the matching credit-note lines' net (LineTotal − TaxAmount) off revenue; sale-order rows unchanged (tested). **R7 margin analysis needs no change**: it is the *expected* margin of sale orders against their purchase orders, read only from Demand (SO lines' DiscountPercent, PO prices) — POS sales and returns never reach it (tested: R7 output identical before/after a POS sale + return); POS realized margin is in R8 and product profitability. QuickBooks: POS invoices publish like any; credit notes are offered and refused by the gateway as before (existing rule, no gateway change); refunds/payments are not synced (R-2).
- **D-40 (FIN) Migration `20261010144347_A38_CounterSales`** (guarded/idempotent SQL: COL_LENGTH/OBJECT_ID/sys.indexes checks; the two NOT NULL→NULL changes drop and re-create the indexes on the column). Additive; existing rows default to SALE_ORDER. Finance `SalesInvoiceListItemModel.SaleOrderUuid` / `SalesInvoiceLineModel.SoLineUuid` are now nullable in the API (frontend types should allow null), plus `sourceType`, `sourceNumber`, `originalInvoiceUuid`, `returnedAmount`, line `discountAmount`/`taxAmount`.
- **D-41 (POSB) Calculator.** One pure static class `PosTotalsCalculator` (§1 verbatim). The order-discount remainder goes on the last line whose net ≠ 0 (a zero line never goes negative). Tenders are checked in the order sent. Worked examples E1–E9 in the contract appendix are the shared test vectors.
- **D-42 (POSB) Online refuses, offline accepts.** Business rules (shift CLOSING/closed, unusable variant, inactive customer, discount permission, tender mismatch, credit) answer 400 online and are accepted with a warning/flag offline — the sale already happened. Malformed data, unknown terminal/shift/customer/variant and reused payment ids are refused either way (cannot be stored or posted). A late offline order on a closed shift is booked to it with a `System:` line in `reconcileNotes`; totals/variance recomputed, status unchanged. An offline tender mismatch reaches Finance normalised (excess off the last tenders, shortfall ON_ACCOUNT on the order's customer — a receivable a supervisor can see). The pushing user must be active store staff or hold POS_STORE_MANAGE.
- **D-43 (POSB) Credit.** Check order: feature → walk-in (`isSystem` or code C-WALKIN/WALK_IN) → `allowPosCredit` → `maxSingleCreditOrder` → limit (credit limit 0 = no credit). Offline limit = (override ?? limit) × (1 + tolerance %), balance = server balance at sync time (a batch runs in `createdAtLocal` order, so earlier offline credit counts). Any offline breach ⇒ CREDIT_OVER_LIMIT + `POS_CREDIT_OVER_LIMIT` to the store's SUPERVISOR staff (D-34 recipients, never a role broadcast). Every offline ON_ACCOUNT ⇒ OFFLINE_CREDIT.
- **D-44 (POSB) Postings.** `PosPostingService` (shared by sync, void, return and the retry job) brings an order's postings up to its state; each call idempotent: stock on (order uuid, POS_SALE/POS_VOID) or (return uuid, POS_RETURN); Finance sale on the order uuid, return on the return uuid, void on a uuid **derived** from the order uuid (MD5 of uuid + "VOID": stable across retries, no column needed). A void of a sale already in Finance calls `VoidSaleAsync` **before** the order changes, so Finance's refusals (D-38) surface as 400 unchanged; a void of a sale never posted posts sale + reversal later (net zero). A return waits (PostingError, retried) until its sale has an invoice; the retry job goes in id order. A 0.00 sale is not invoiced (Finance refuses a sale for nothing). Invoice date = `createdAtLocal` (clamped to the receipt time). `customerPaymentUuid` mapped by position (one Finance payment per non-ON_ACCOUNT tender, in the order sent). Finance does not call `IPosChangeListener`: POS pushes `CustomerBalanceChanged` itself after an ON_ACCOUNT sale/void/return.
- **D-45 (POSB) Returns.** Optional `shiftUuid` (OPEN shift of the same store), default the original terminal's OPEN shift. Line amount = `round(lineTotal × qty / originalQty)`; the last remaining units take exactly what is left (Finance refuses over-crediting a line, D-37) — FEPOS/FEBO's Σ round(...) estimate must apply the same remainder rule (published with an example). Refunds must equal the total exactly. ON_ACCOUNT refunds ≤ the on-account amount not yet refunded on account. The original's `ReturnedQuantity` changes only once every rule passed.
- **D-46 (POSB) Cashier & offline sessions (FEPOS request).** `SyncOrder.cashierUserId` honoured when the user is active staff of the store, active, with POS_ORDER_CREATE; else the pusher + warning. The pusher is stored in new `pos.orders.SyncedByUserId` (guarded migration `20261010151222_A38_PosOrderSyncedBy`). Offline orders with an unknown session attach to the session with `sessionLocalId`, else the cashier's latest session on the shift, else a new **closed** session (start = end = `createdAtLocal`) so the terminal's live session is never displaced. POSA's sessions `localId` race fixed: the loser answers the winner's session.
- **D-47 (POSB) Jobs.** `PosPostingRetryJob` every 15 min, backoff 15 min × 2^(attempts−1) ≤ 1 day, batch 200, organizations without MODULE_POS excluded; it **always** sets `HangfireTenantScope` per organization (unlike `RunForEnabledOrganizationsAsync`, which runs unscoped when every org is enabled), for INV R-6 and Finance's own-organization check. `NegativeStockReportJob` daily 06:00 UTC per active store, one notification per supervisor, up to 10 SKUs.
- **D-48 (POSB) Catalog price = variant SellingPrice.** D-6's per-store `IPricingService` resolution is **not** done: it resolves one variant at a time and price-list edits do not bump the variant's ModifiedAt, so deltas would miss them. POS sells at SellingPrice; PRICE_CHANGED compares with it. Revisit with a price-list change feed (R-8).
- **D-49 (POSB) Sync paging over two sources.** Catalog and customer deltas merge the master source with `product_pos_settings` / `customer_pos_settings`; a page ends at the earlier last timestamp of a full source and includes everything up to and including it (ties too), so `nextSince` never skips equal timestamps. Settings saves always bump ModifiedAt. PIN hashes only to the bound device (`X-Pos-Device`), only active PIN holders with POS_ORDER_CREATE.
- **D-50 (POSB) Order read access.** POS_ORDER_VIEW, or POS_ORDER_CREATE as the order's cashier or active staff of its store (receipt reprint / history on the till).

## Residuals / findings outside A38
- R-1 `NotificationService.CreateForRoleAsync` / `BroadcastAsync` (raw SQL) have **no organization filter** — a role notification reaches users of every org. Not used by A38; should be fixed separately.
- R-2 QuickBooks: customer payments and credit notes are not synced. **Decided 2026-10-10 ("Sync POS sales"):** POS invoices
  go to QuickBooks only when the per-organization switch `IntegrationSettings.AutoPushPosSales` is on (default **off** for
  new and existing orgs; migration `QBI_AutoPushPosSales`) *and* "Sales invoices" is on — POS payments are not synced, so
  the sales appear in QuickBooks as open A/R invoices and the admin opts in. While off, the gateway **holds** each POS sale
  (payload stored, map `LastErrorCode = POS_SALES_HELD`, nothing queued, no dependencies requested); the settings API
  reports `posSalesWaiting`. Turning it on (and every hourly reconciliation while on) asks Finance for every held sale
  again — queued once, idempotent. A held sale cancelled before it was ever sent sends nothing. Turning it off again holds
  queued-but-unsent POS sales; what QuickBooks already has stays. Only POS payloads carry `SourceType = "POS"` (back-office
  payloads and fingerprints unchanged). Details: `docs/quickbooks/QUICKBOOKS-INTEGRATION-PLAN.md` (Implementation status).
  Payments and credit notes remain unsynced.
- R-3 Catalog sync `taxCodes` come from Lookups, not Finance TaxCode (A37 R-4) — POS must use Finance tax codes.
- R-4 `Product.IsSaleable` and `IsAvailableForPos` are not enforced anywhere today.
- R-5 (INV) **FIXED 2026-10-10.** `GoodsIssuePoster` used to floor QtyOnHand at 0, so a delivery issued after a POS oversale silently erased the shortfall (the ledger kept it). Now on-hand takes the full issued quantity and may go (further) negative; QtyReserved keeps its floor at 0. Rows with enough stock behave exactly as before. Regression: `PosThenGoodsIssueTests` (10 on hand, 6 reserved, POS sale 8 → 2; issue 6 → −4, reserved 0, ledger out 6). The old `On_hand_is_never_driven_negative` test now asserts −60 instead of 0 (renamed `A_short_row_goes_negative_by_the_issued_quantity_instead_of_being_floored`).
- R-6 (INV) The ledger service reads its running balance and the master product ledger stamps its org from the *ambient* tenant — fine for POS calls in a request; a Hangfire caller without a tenant would get a 0 starting balance / empty org on the master row. `PosStockPoster` stamps the org on its own inventory ledger rows.
- R-8 (POSB) Store price lists are not applied on POS (D-48).
- R-10 (QA) Root cause of the "SqlServerRetryingExecutionStrategy does not support user-initiated transactions" bug: `MasterProductLedgerService.PostMovementAsync` enlists the request's FinanceDbContext in Inventory's transaction and never detaches it. CounterSaleService now releases a finished transaction (fixed for POS); any *other* request that writes the master/product ledger through Inventory and then saves Finance again would hit the same error.
- R-11 (COORD) The PWA device keeps the supervisor's own session (7-day rolling refresh) for sync, PIN sign-in and the hub — whoever holds a bound device holds those permissions (alongside the D-4 offline PIN-hash risk). Mitigation is operational: unbind lost devices.
- R-12 (COORD) Sales-invoice DTO has no `sourceUuid`; the back office finds a POS invoice's order by number.
- FIXED (COORD, after QA): PIN sign-in now needs a POS permission (POS_ORDER_CREATE / POS_SHIFT_OPEN / POS_TERMINAL_MANAGE) — no longer any org user; grace period: order sync is `[AllowDuringGrace]` (offline/late sales of open shifts land), opening a shift and creating a terminal are `[BlockDuringGrace]` (new Shared markers honoured by FeatureAuthorizationFilter).
- R-9 (POSB) `/sync/stock` is a full warehouse snapshot per call (no stock delta source); fine at store sizes.
- R-7 (INV) `PosCatalogSource.GetChangedAsync` orders by the later of two ModifiedAt columns, so the A37 (OrganizationId, ModifiedAt) indexes are not seekable — a scan of the org's variants per delta; fine at store-catalog sizes, revisit if catalogs grow large.
