Builds on SCM Finance (A29 receivables, SAP-alignment payables, A35 multi-currency), A42 GL, A44 posting gateway, A47

## Part A — Reality check

| D-AR-1 | Credit limit for the SO / invoice check: `BusinessPartner.CreditLimit` null or 0 = **no limit** (TS-CR-001, D-CORE-3). POS keeps its own on-account rule (null/0 = no POS credit) — untouched. A temporary limit needs a permanent one and must exceed it; effective = MAX while live (CORE's `CreditLimits`). |
| D-AR-2 | Exposure (base, live, `CreditExposureReader`): open orders = Demand orders CONFIRMED / PARTIALLY_FULFILLED / FULFILLED, the un-invoiced share (Qty − InvoicedQty) of each line total, scaled to the grand total, at the order's locked rate (GrandTotalBase/GrandTotal, else ExchangeRate, else 1); + open invoices = ISSUED / PARTIALLY_PAID / OVERDUE `BalanceDue` × rate; − unapplied credit (RECEIVED payments' unallocated part, credit notes' remaining), floored so the invoice part never goes below 0. A draft invoice stays in open orders (InvoicedQty moves at issue). The sales-invoice check moves its amount from orders to invoices, so billing an approved order never "adds" exposure (task 120). |
| D-AR-3 | Sale-order confirm (Demand edit, behind mode): a probe `CheckAsync` (Off → one settings read, no lock, confirm unchanged); otherwise `LockCustomerAsync` is taken **before** the order's hold lock and held until the confirm committed; the real check runs inside the confirm after the gates and the rate lock and before any reservation, amount = GrandTotal in base via the rate lock. Refusal = 409 contract text; CREDIT_OVERRIDE (claim) + `creditOverrideReason` confirms, the `Override` row is written after commit (best effort, logged — never un-confirms). Result gains `creditCheck` / `creditWarning`. The 2-argument confirm (tests, internal callers) checks too, without override. |
| D-AR-4 | Sales-invoice creation: warning only, after the commit, never failing it — `SalesInvoiceCreated.CreditWarning` (hold reason or over-limit text) and appended to the response message. |
| D-AR-5 | Customer lock (TS-CR-008): an in-process semaphore per (org, customer) always, plus on SQL Server an exclusive **session** `sp_getapplock` (`finance.credit/{org}/{customer}`, 15 s → 409) on a connection of its own, released on dispose (closing the connection releases it too). Credit-memo create/apply serialize per customer with a transaction-owned app lock inside the execution strategy. |
| D-AR-6 | BR-CR-005 expiry is lazy: an expired temporary limit is cleared (with a `TempExpired` row) when exposure is read; the check itself ignores an expired one. Clearing a temporary limit by hand (`amount: null`) is a `TempIncrease` row with new value "None". Every hold / release / temp / tier / override / dunning hold / reset writes `credit_hold_requests` (BR-CR-006). |
| D-AR-7 | Dunning day = the UTC date (one non-cancelled run per org per UTC day). | D-AR-8 | Dunning charge (D-10): an ISSUED SalesInvoice, `SourceType DUNNING_CHARGE`, number `SDC-yyyyMMdd-NNNN`, one non-stock line (VariantUuid empty), sale base at the locked rate, due the same day, `SourceUuid` = the run item (idempotent), customer-ledger **INVOICE** debit with reference SalesInvoice (so RPT's aging/statements and later dunning see it), no product ledger; after commit posted through A44 as a sales invoice (Dr RECEIVABLE / Cr REVENUE, TS-DN-007). |
| D-AR-9 | Auto-reset (BR-DN-006) runs at every preview: profiles above level 0 whose customer has no open invoice go to 0 (`DunningReset`, "Balance cleared"). | D-AR-10 | Procedures: code unique per org (upper-cased), levels replaced as a set (1..n, no gaps), block-sales level within 1..n; creating/updating a default clears the old default; the default cannot be un-defaulted or deactivated by PUT (409). |
| D-AR-11 | AR credit memo (C7, D-6): a CREDIT_NOTE SalesInvoice, `SourceType AR_CREDIT_MEMO`, number `SCN-…` (A38's prefix), **financial only** (no stock moves — a goods return is the POS / sales-return path); amount lines (gross), tax carved out from the line's tax code (or the original line's rate); A38-style CREDIT_NOTE ledger credit for the whole total at creation; `original.ReturnedAmount += total`, refused above the invoice total; posted after commit through A44 as a credit memo (Dr REVENUE + TAX / Cr RECEIVABLE, TS-CM-001). Additive request fields: `applyToOriginal` (default true → applied at once up to the original's balance) and line `invoiceLineUuid` (carries the product so QuickBooks has an item); plus `GET api/finance/ar/credit-memo/{uuid}`. |
| D-AR-12 | Applications: **every** A48 application — including to the memo's own original invoice — writes a `customer_credit_applications` row; both documents' `CreditedAmount` rise, the invoice's `BalanceDue`/status follow A38's rule; **no ledger entry** (the note's credit was booked once, at creation; A38 applications write none either). Remaining = \|GrandTotal\| − CreditedAmount − refunds (A38 notes carry a positive GrandTotal). **RPT as-of rule:** credit on invoice *i* = Σ live application rows targeting *i* (by AppliedAt) + for notes with `OriginalInvoiceUuid = i`: `note.CreditedAmount − Σ that note's rows` (= A38's direct application). |
| D-AR-13 | QA-3 / contract §3 — reads report the **effective** dunning level: 0 when the customer has no open invoice (ISSUED / PARTIALLY_PAID / OVERDUE with BalanceDue > 0 — the same test as the persisted auto-reset), else the stored level. Applied in the partner-profile get / list (incl. the `minDunningLevel` filter) / update responses and the dunning customer history (`EffectiveDunningLevel`). Reads never write: the stored level, its `DunningReset` audit row and `LastDunningDate` change only at the next preview (no write on GET, no race). The credit exposure model carries no dunning level. |
| D-AR-14 | QA-5 — one credit ceiling per invoice: credits (POS returns, AR credit memos, credit notes = `ReturnedAmount`) ≤ GrandTotal. Finance exposes it on the POS↔Finance contract as `ICounterSaleService.GetCreditableRemainingAsync(org, invoice)` (default implementation → null for other fakes) and keeps its own posting guard (`CounterSaleService.CreditableRemaining`). The POS return / exchange path reads it before anything is recorded: **online** → 400 "This return would credit more than the invoice total: … above its total (only x remaining …)", no order, no refund; **offline / synced** (the cash already left the till) → accepted with the `PolicyOverriddenOffline` flag and the same text as a warning, so the till and the order show it; its Finance posting is then refused by the guard and stays in the POS posting errors for an accountant (residual: no automated resolution). An unposted sale (no invoice yet) is not checked up front. |
| D-RPT-1 | One open-item engine (`ArAp/Reporting/SubledgerOpenItems.cs`) behind aging, balances, open items, DSO/DPO, statements and vendor reconciliation — not a second copy of A29 R3: its AR rules **are** R3's (issued/opening invoice counts from its ledger entry; payment by payment date unless its bounce is booked by then; cancelled = owed only before the cancellation; drafts never), proved equal by `New_aging_agrees_with_the_existing_A29_R3_report`. Existing endpoints (`api/reports/aging-receivables`, `api/suppliers/{id}/aging`, `api/reports/supplier-aging`) untouched. Open amount per document computed in SQL (correlated sums; `IgnoreQueryFilters` + explicit `OrganizationId` so predicates seek), only open documents come back, bucketing/roll-up over that projection; bounced-payment ids read once and passed as a list (the per-allocation ledger probe doubled the 10k time — the ledger has no ReferenceId index). LocalDB, best of 3 after warm-up: AR 10 000 open (half part-paid, + 5 000 of another org) **295–730 ms**, AR 50 000 **1.3–1.9 s**, AP 10 000 (half part-paid) **183–309 ms** (targets 2 s / 5 s / 2 s). |
| D-RPT-2 | Credits are open items: AR = RECEIVED payments' unallocated part (not bounced by then) + customer credit notes (A38 POS notes and AR_CREDIT_MEMO `SCN-…`) remaining = GrandTotal − CreditedAmount (+ applications made after the day) − refunds; AP = advances' AvailableBalance, CARRIED_FORWARD credit/debit notes (`CarriedForwardAmount ?? amount`, live debit-note statuses), APPROVED bad-debt write-offs. In aging they sit **beside** the buckets (`unappliedCredits`, `netBalance`); open items / statements show them signed (negative). - R-1 Withholding tax, SEPA/ACH files, bank reconciliation, customer portal — deferred by the FSD.

### Migration `20261025030029_A48_ArApSubledgers` (focus 1): no blocker

**Guards and transaction**
- Every Up statement is guarded on its own: `COL_LENGTH`, `OBJECT_ID`, `sys.indexes`, `sys.check_constraints` and `sys.foreign_keys`.
- It runs in EF's migration transaction, so a partial run is rolled back, not left half done.
- Column CHECKs are added after their column, and existing rows get the default value (`Off`, `SRO`, 0), so the CHECKs pass on existing data.
- The new columns are all additive: nullable, or NOT NULL with a default.
- Down uses EF's `DropColumn`, which drops the unnamed default constraints itself. Its order is valid: FK → tables → CHECKs → indexes → columns.

**Indexes on existing tables**
- I scanned every migration in all modules for `AlterColumn` / `DropColumn` / raw `ALTER COLUMN` on `finance.invoices` / `customer_ledger` (D-CORE-16).
- The only hits on indexed columns are older **Down** methods (`AddPaymentPosting` drops PaidAmount; `AddOrganizationIdTenantScoping` drops OrganizationId). They can only run after A48's Down has dropped the two indexes, so they are not a hazard.
- No other module alters these tables.
- All key columns are bounded types (nvarchar(20/30/50), uniqueidentifier). No nvarchar(max) is in a key.
- `IX_invoices_VendorInvoiceNo` is non-unique, as D-CORE-6 requires.

**Seeds**
- Seeds come from `tenant.Organizations` and are guarded on that table existing.
- An org that already has a default procedure or rule is left alone.
- Levels are added only to STANDARD procedures that have none, which covers a prior run that stopped between the procedure insert and the level insert.

**Backfill**
- `remaining` = InvoiceSettlement without the unposted lines.
- It skips deleted, reversed and paid invoices, and invoices that already have a schedule.
- Trimmed / mixed-case statuses are handled, and the test covers them.
- Re-runs are idempotent: the unique `IX_payment_schedules_InvoiceId`, plus `NOT EXISTS`.
